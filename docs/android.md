# 안드로이드 앱

웹은 Cache Storage 보관함과 파일 다운로드를 제공합니다. Android 앱은 저장·PDF
뷰어·타이머·팝업·위젯·네이티브 로그인 등을 처리합니다. 현재 앱은 10.1 / 92입니다. 받은 파일은 **앱 데이터 폴더**에 회차별 하위 폴더로 들어갑니다.

```
Android/data/kr.gijul.direct/files/
  2026 7월 학평(인천) 생명과학Ⅰ/
      … 문제.pdf   … 정답.png   … 해설.pdf
```

권한을 물을 필요가 없고, 앱을 지우면 함께 정리됩니다. 대신 **안드로이드 11+에서는
다른 파일 관리자가 이 경로를 열 수 없으므로**, 앱이 목록과 열기를 직접 제공합니다 —
회차 목록 위의 **받아둔 자료** 버튼입니다. 열기는 앱 안 뷰어가 담당하고 **다른 앱으로 열기**에서는
FileProvider의 `content://` URI와 파일에 맞는 MIME 타입을 넘깁니다.

페이지는 `window.GijulNative`가 있을 때만 이 앱 폴더를 씁니다. 다른 OS·브라우저도
`Vault` 어댑터의 웹 보관함과 받아둔 자료 화면을 사용할 수 있습니다.

## 문제지 읽기

문제·정답·해설은 **앱 안에서 엽니다.** WebView에는 PDF 뷰어가 없어 처음에는 기본
브라우저로 넘겼는데, 자료를 열 때마다 앱이 크롬으로 바뀌는 건 이 앱의 요점을 잃는
일이었습니다. `PdfRenderer`로 직접 그립니다 — 페이지는 `RecyclerView`로 필요한 것만
그리고(20쪽짜리를 통째로 비트맵으로 들면 메모리가 남아나지 않습니다), 확대는 다시
그리지 않고 뷰 변형으로 처리해 손가락을 따라옵니다. PNG/JPG 정답지는 샘플링해 디코딩하여 큰 이미지의 메모리 사용을 제한합니다.

흔한 PDF 뷰어들이 쓰는 두 겹 구조를 따랐습니다.

| | 무엇을 | 어떤 크기로 |
|---|---|---|
| **밑그림** | 열 때 전 쪽 한 번 | 280px 고정 (장당 0.45MB) |
| **본그림** | 보는 쪽과 바로 앞뒤만 | **화면에 놓일 크기와 1:1** |

두 번째 줄이 핵심입니다. 표시될 폭보다 작게 그리면 늘려서 붙이게 되고 그것은 결국 흐린
화면입니다. 그래서 **메모리가 모자랄 때 낮추는 것은 해상도가 아니라 들고 있는 장수**
입니다. 확대는 손짓 도중에는 뷰 변형으로 따라가고, 손을 뗀 뒤 그 배율로 다시 그립니다.

고해상도를 보이는 쪽에만 쓰는 것도 같은 이유입니다 — 한 장이 수십 MB인 마당에 멀리까지
미리 그려봐야 서로를 밀어낼 뿐이고, 나머지 쪽은 밑그림이 즉시 받아 줍니다.

**축소는 1배 아래로도** 내려가 양옆에 여백이 생기며, 그만큼 여러 쪽이 한눈에
들어옵니다. 확대·축소는 손가락 사이를 중심으로 돌고, 여백이 생겨 가운데로 세워야
할 때는 손을 뗀 뒤에 합니다 — 손짓 중에 정렬하면 화면이 손에서 미끄러집니다.

화면에는 현재 쪽(`3 / 16`)과 배율이 뜹니다. 배율을 누르면 **폭 맞춤 ↔ 쪽 맞춤**을
오갑니다 — 문항을 읽을 때와 한 쪽을 통째로 훑을 때가 서로 다른 배율입니다.
**가리기**를 누르거나 화면을 한 번 두드리면 막대와 시스템 표시줄이 사라지고, 다시
두드리면 돌아옵니다. 뒤쪽까지 내려가면 **맨 위로** 단추가 나타납니다.

### 그려 둔 쪽을 얼마나 들고 있는가

띄워 둔 창은 캐시를 **쪽수가 아니라 킬로바이트로** 셉니다(허락된 것의 1/8,
6~24MB). 폭 1600짜리 한 쪽이 ARGB_8888로 14MB 가까이 되므로 '넉 장'이라고 하면
50MB가 넘습니다. 이 창은 남의 앱 위에서 몇 시간씩 사는 것이라, 그만큼을 붙들고
있으면 정작 쓰던 앱이 대신 죽고 사용자 눈에는 그 앱이 잘못한 것으로 보입니다.
한 쪽이 8MB를 넘지 않도록 넓이로도 묶습니다 — 해설지에는 한 쪽이 화면 서너 배
높이인 것이 있습니다. `onTrimMemory`가 오면 그려 둔 것을 놓습니다(보던 자리와
배율은 그대로입니다).

손을 떼면 **미끄러집니다**. 뷰어 쪽은 `RecyclerView`가 알아서 하는 일을 이쪽은
직접 그리므로 `OverScroller`로 직접 합니다.

### 스크롤 막대

오른쪽 가장자리의 짧은 알약 하나입니다. **길이는 쪽수와 상관없이 고정**인데,
'얼마나 남았는가'는 잡았을 때 뜨는 말풍선이 `13 / 20`으로 말해 주므로 막대까지
길이로 되풀이할 것이 없어서입니다. 잡으면 4dp에서 9dp로 두툼해집니다.

흰 테를 먼저 깔고 먹을 얹습니다. 이건 문제지 **위에** 얹히는 것이라 그림이나
표처럼 검은 자리에 걸리면 먹만으로는 묻힙니다 — ㄴ자 손잡이가 안 보였던 그
일입니다. 어느 바탕이든 둘 중 하나는 보입니다.

보이는 굵기는 4dp지만 **잡히는 폭은 22dp**입니다. 4dp를 손가락으로 겨누게 하면
대개 빗나갑니다. 알약 밖을 누르면 그 자리로 먼저 뜁니다.

말풍선을 막대 **왼쪽**에 붙이는 것은 위에 얹으면 잡은 손가락에 가려서입니다.
위 막대의 쪽수 표시와 겹치는 것 같지만, 그쪽은 화면을 두드려 감추면 함께
사라집니다. 훑는 동안 쪽수를 알려주는 것은 이것뿐입니다.

값은 `FloatService.SB_*` 한 곳에 있고 뷰어가 그것을 가져다 씁니다. 띄워 둔 창의
막대와 뷰어의 막대는 같은 것이어야 합니다.

이미 받아둔 자료에 같은 파일이 있으면 그걸 씁니다. 필기 앱·인쇄로 넘길 때를 위해
화면 위의 **다른 앱** 버튼을 남겨뒀습니다. EBSi 사이트 링크처럼 자료가 아닌 주소는
그대로 브라우저 몫입니다.

앱은 사이트를 그대로 불러오므로 페이지를 고쳐도 APK를 다시 만들 필요가 없습니다.

창 크기와 자리는 **한 번 맞추면 그대로 남습니다**. 두 벌로 적습니다 — 화면 크기를
열쇠에 넣은 한 벌이 있어서 세로에서 맞춘 것은 세로에서, 가로에서 맞춘 것은
가로에서 제 크기로 돌아옵니다. 그리고 열쇠 없는 **마지막 한 벌**이 따로 있어,
처음 보는 화면(처음 돌려 본 가로, 바꾼 폰)에서도 기본값이 아니라 마지막 크기를
화면에 맞게 줄여 씁니다. 빌려 온 크기일 때는 자리까지 빌리지 않고 가운데에
놓습니다.

## 시험 시간 재기

문제지를 여는 것과 실전처럼 재는 것은 다른 일입니다. 지금까지는 폰 시계를 따로
켜야 했습니다.

**시작은 뷰어의 아이콘입니다.** 띄우기·다른 앱으로·가리기 셋보다 **앞**에
둡니다 — 읽기 전에 누르는 것이라 그렇습니다. 처음 누르면 시간을 한 번 묻고,
고른 것은 그 과목에 기억되므로 다음부터는 누르는 즉시 시작합니다(다시 고르려면
길게 누릅니다).

### 하나의 시계, 세 얼굴

| 어디 | 무엇 |
|---|---|
| 뷰어 | 막대 안 남은 시간 + 그 아래 줄어드는 실선 |
| 띄운 창 | 손잡이 줄에 시간만 (새로 뜨는 것 없음) |
| 나갔을 때 | 알림 — 잠금화면과 나우바에도 |

셋이 저마다 세면 조금씩 어긋나고 **어긋나는 것을 아무도 못 봅니다.** 시간은
`Timing` 한 곳에서만 흐르고 셋은 그것을 읽어 그릴 뿐입니다.

### 시각을 들고 있지 시간을 세지 않습니다

1초마다 남은 시간을 빼 나가면 화면이 꺼져 있는 동안, 앱이 잠든 동안, 프로세스가
죽었다 살아난 동안이 통째로 사라집니다. 그래서 **언제 시작했는지**만 적어 두고
남은 시간은 물어볼 때마다 셈합니다(`Clock`). 일시정지는 '멈춘 만큼 시작 시각을
뒤로 미는 것'으로 다룹니다 — 멈춘 채로 프로세스가 죽어도 되살아난 뒤 셈이
같습니다.

알림의 숫자는 **시스템이 셉니다**(`setUsesChronometer` + `setChronometerCountDown`).
끝나는 시각만 건네면 우리가 잠들어도 흐르고, 잠금화면이나 나우바처럼 우리가
손댈 수 없는 자리에서도 같이 흐릅니다.

> **나우바는 삼성 것입니다.** 어떤 알림이 거기 올라가는지는 One UI 판본이
> 정합니다. 우리가 하는 것은 그쪽이 집어 올릴 만한 모양으로 내는 것뿐이고,
> 안 올라가더라도 알림 자체는 뜹니다.

### 못 하는 것

0이 되는 순간의 소리·진동은 **우리 프로세스가 살아 있을 때만** 울립니다.
정확한 알람은 안드로이드 12부터 따로 권한을 물어야 하는데, 시험 한 번 재자고
그것을 묻는 것은 값이 맞지 않습니다(위젯의 자정 알람도 같은 까닭으로 정확하지
않게 두었습니다). 숫자는 어느 경우에도 계속 흐르므로 넘긴 것은 보입니다.

### 잰 시간은 회차에 남습니다

끝내면 `92분 · 8분 남김`처럼 표시 옆에 붙습니다. 타이머가 끝나는 때에 페이지가
떠 있으리라는 보장이 없으므로, 앱이 적어 두었다가 페이지가 뜰 때 통째로
넘깁니다. `peekTimings()`로 읽고 JS 저장 성공 뒤 `ackTimings(ids)`로 지웁니다.
현재 앱의 호환 메서드 `takeTimings()`도 읽을 때 삭제하지 않습니다. 구형 앱에는
이전 전달 방식으로 돌아갑니다. 회차 표시의 주인은 페이지입니다 — 과목 번호와 열쇠를
아는 쪽이 거기라, 앱이 직접 고치면 규칙이 두 벌이 됩니다.

그러려면 뷰어가 **어느 회차인지** 알아야 하는데 주소만으로는 알 수 없어서,
`openPaperAt(url, name, grade, sub, key)`을 따로 냈습니다. 있던 메서드에 인자를
더하지 않은 것은, 그러면 옛 앱에서 맞는 메서드가 없어 통째로 실패하기
때문입니다 — 페이지가 앱보다 먼저 갱신되므로 그 사이 자료가 안 열립니다.

## 띄워 두기

뷰어의 **띄우기**를 누르면 문제지가 다른 앱 위에 얹힙니다(`FloatService`,
안드로이드 8.0부터·'다른 앱 위에 표시' 권한). 필기 앱을 쓰면서 문제지를 곁에
두려는 것이 요점이라, 기본은 **터치가 그대로 밑으로 통과하는** 상태입니다.

**띄우면 앱은 물러납니다.** 요점이 '다른 앱을 쓰면서 문제지를 곁에 두는 것'이라
뒤에 우리 화면이 남으면 그 앱으로 가는 데 한 걸음이 더 듭니다. 되부르는 길은
아래 ☰ 항목에 있습니다.

액티비티의 `finishAndRemoveTask()` 만으로는 모자랐습니다. 그것은 '내가 속한
태스크'를 지우는데, 시작 화면이 `singleTask` 라 기기에 따라 문제지 화면과 다른
태스크에 서는 수가 있습니다 — 그러면 문제지 화면만 닫히고 뒤에 앱이 그대로
남습니다. `ActivityManager.getAppTasks()` 는 우리 앱의 태스크를 **전부**
돌려주므로 어느 쪽이든 걸립니다.

창은 셋으로 나뉩니다 — 위의 조작 바, 종이, 좌하단의 ㄴ자 손잡이. 바에서 통과와
조작을 오가고, 슬라이더로 투명도를 정하며, 창 크기는 손잡이로 바꿉니다. 자판이
뜨면 손잡이는 물러납니다 — 대개 자판 위에 겹쳐 앉아, 글자를 치는 내내
걸리적거립니다.

**조작일 때 종이를 다루는 손짓**은 뷰어와 같습니다. 이 창에는 확대 단추가
없습니다 — 높이가 글꼴에 맞춰지는 바에 자리가 없어 뺐고, 그래서 손짓이 유일한 길입니다.

| 손짓 | 무엇이 |
|---|---|
| 두 번 두드리기 | 2배 ↔ 폭 맞춤. 두드린 자리를 붙들고 0.21초에 걸쳐 옮깁니다 |
| 두 번째 두드림을 그대로 끌기 | 한 손으로 배율 잡기(quick scale) |
| 손가락 둘로 벌리기 | 그 사이를 붙들고 확대 |
| 끌다 놓기 | 미끄러집니다 |
| 오른쪽 가장자리 | 스크롤 막대 — 아래 항목 |

두 번째 두드림을 **끌면 그건 두드림이 아닙니다.** 16dp 넘게 움직였으면 한 손
확대로 넘깁니다 — 그러지 않으면 끌기 시작하는 순간 2배로 튀었다가 거기서부터
확대됩니다. 그 손짓으로 끝난 뒤에는 미끄러뜨리지도 않습니다. 손가락 하나가
위아래로 지나간 것이라 그대로 두면 놓는 순간 종이가 달아납니다.

오른쪽 끝의 **－**는 창을 접습니다. 종이와 손잡이는 숨기고 잡는 표시·펼치기·닫기와
실행 중 타이머를 남깁니다. 최소화된 창의 폭은 고정값이 아니라 버튼·시간 글자를
측정하여 정하며, 창과 흰 테두리를 함께 조절합니다. 남은 시간의 자릿수나 큰 시스템
글꼴 때문에 버튼이 테두리 밖으로 밀리지 않도록 높이도 글꼴에 맞춥니다.
핵심 버튼과 실행 중 타이머의 터치 영역은 최소 48dp이며 의미 있는 접근성 이름을 둡니다.

팝업과 PDF 뷰어 모두 남은 시간을 누르면 조작 메뉴를 엽니다. 바로 일시정지하지
않으며, 일시정지/재개·끝내기를 메뉴에서 선택합니다. 10분 추가 기능은 없습니다.
네이티브 시트는 화면 높이를 제한하고 스크롤할 수 있습니다.

접는 애니메이션은 내용 교체와 위치 이동을 함께 처리합니다. 펼친 창의 위치·크기를
유지하여 다시 펼치면 보던 문제지 자리와 배율로 돌아옵니다. API 36 에뮬레이터에서
font scale 1.0/2.0의 최소화 창을 확인했으며 모든 기기·분할 창 조합을 확인한 것은 아닙니다.

**투명도는 통과일 때 스스로 깎입니다.** 안드로이드 12부터 창이 흐릿하게 겹쳐
있으면 그 아래로 가는 터치를 시스템이 통째로 버립니다(합친 불투명도 0.8이 상한,
`InputManager.getMaximumObscuringOpacityForTouch()`). 그래서 통과일 때는 그 값까지만
올리고, 조작으로 바꾸면 정한 값이 그대로 돌아옵니다.

### 움직이는 것들

문제지 위에 얹히는 것이라 절제해서 씁니다. 바뀌는 것이 **무엇에서 무엇으로**인지
눈이 좇을 데가 없을 때만 넣었습니다.

| 어디 | 무엇이 | 왜 |
|---|---|---|
| 통과 ↔ 조작 | 칠이 미끄러진다 | 어느 쪽이 켜졌는지가 칠 하나로만 구별된다 |
| 통과로 돌아올 때 | 손잡이가 상한까지 미끄러지고 종이가 함께 흐려진다 | 값만 갈아 끼우면 화면이 왜 밝아졌는지 안 보인다 |
| 목록 열기 | 12dp 아래에서 떠오르며 든다 | 종이와 같은 자리를 나눠 쓴다 — 갈아 끼우면 종이가 어디 갔는지 모른다 |
| 막대 잡기 | 4dp → 9dp, 말풍선이 든다 | 툭 바뀌면 잡힌 것인지 손이 미끄러진 것인지 모른다 |
| 목록의 줄·단추 | 눌린 동안 짙어진다 | 눌러도 받아 오는 동안은 화면이 안 바뀐다 |
| 맨 위로 | 흐리게 뜨고 진다 | 문제지 위에 툭 나타나면 놀란다 |

접기는 위의 `foldT` 하나가 전부입니다.

### 목록

바 왼쪽의 **☰** 는 종이 자리에 문서 목록을 띄웁니다(`PickerView`). 보던 회차의
다른 자료뿐 아니라 **전체 목록**을 훑을 수 있어서, 앱으로 돌아가지 않고도 다음
문제지로 넘어갑니다. 화면은 둘뿐입니다 — 과목 고르기와 회차 고르기.

처음 열면 **보고 있던 과목의 회차부터** 펼칩니다. 찾던 것은 대개 거기 있고,
아니면 '‹' 한 걸음이 전체 목록입니다. 어느 과목에서 왔는지는 페이지가 알려
줍니다(`openPaperIn`) — 주소만으로는 알 수 없습니다. 회차 파일이 과목마다 따로라
주소 하나가 어느 과목 것인지 되짚으려면 과목 파일을 전부 받아 뒤져야 합니다.
과목 페이지(`s/`)는 제 주소에서 읽습니다. 그 창구가 없는 옛 앱은 옛 길로
그대로 가고 전체 목록에서 시작합니다 — 인자를 더 붙인 채로 부르면 맞는 메서드가
없어 호출이 통째로 실패하는데, 페이지는 앱보다 먼저 갱신되므로 그 사이 자료가
아예 안 열립니다.

그 값이 없을 때는 **자료 이름에서 되짚습니다**(`Catalog.byTitle`). 받아둔 자료에서
띄웠거나 아직 옛 페이지가 캐시에 남아 있으면 이쪽이 받습니다 — "2026 6월 모평
생명과학Ⅰ 문제.pdf" 같은 이름에는 과목이 그대로 들어 있습니다. 겹치면 긴 이름이
이깁니다('수학'은 '수학Ⅰ'에 묻힙니다). 학년은 이름에 없어 고3부터 봅니다.

목록을 열어 둔 채로 **☰ 를 1초 누르면 앱 화면이 열립니다**. 과목을 고르는
화면이든 회차를 고르는 화면이든 마찬가지입니다 — 목록을 뒤지고 있다는 것 자체가
'더 넓은 데서 고르고 싶다'는 뜻이라 어느 쪽인지 가릴 이유가 없습니다. 띄우면
앱이 물러나므로 되부를 길이 하나는 있어야 하는데, 높이가 글꼴에 맞춰지는 바에 단추를 더 놓을
자리가 없어 몸짓으로 두었습니다.

손이 머문 지 0.2초가 지나면 **앱 열기**라는 이름이 뜹니다. 아무 표시가 없으면
'누르고 있으면 되는 것'과 '아무것도 아닌 것'이 구별되지 않습니다. 1초를 채우면
진동으로도 알립니다. 앱을 부르면 창은 접혀서 물러납니다. 문제·정답·해설은
셋째 화면으로 빼지 않고 회차 줄에 바로 붙였습니다. 좁은 창에서 한 걸음은 큽니다.

목록은 새로 만들지 않았습니다. 사이트가 이미 `data/`로 같은 자료를 정적 파일로
내보내고 있어, 색인 하나(36KB)와 과목 파일 하나(1~69KB)만 받으면 됩니다
(`Catalog`). 검색은 색인의 `aliases`를 그대로 써서 '언매'·'생윤'이 걸리고,
띄어쓰기를 지우므로 '고3생명'처럼 물어도 됩니다.

**내려받기 통로는 둘입니다.** `MainActivity.download`는 EBSi 주소만 받습니다 —
문제지를 받는 길이 아무 데나 열리지 않게 막아 둔 것이라 넓히지 않습니다. 그래서
목록은 **우리 사이트만** 받는 좁은 통로를 따로 씁니다. 좁은 문 둘이 넓은 문
하나보다 낫습니다. 스쳐 간 문제지는 캐시 폴더에 스물넉 장까지만 남습니다.

## 홈 화면 위젯

여섯 벌입니다. 하나로 합치지 않은 것은 홈 화면의 자리가 사람마다 달라서입니다 —
넷을 나란히 놓는 사람도, 2×2 하나만 두는 사람도 있습니다.

| 위젯 | 크기 | 답하는 질문 | 그림 | 누르면 |
|---|---|---|---|---|
| 달력 | 4×4 | 이번 달에 언제 무엇을 풀었나 | 격자 한 장 | 달력 |
| 이번 주 | 4×2 | 오늘 했나, 며칠째인가 | 막대만 | 달력 |
| 잔디밭 | 4×2 | 어디서 끊겼나 | 칸만 | 달력 |
| 최근 푼 것 | 4×3 | 방금 뭘 풀었더라 | 없음 | 달력 |
| D-day와 진도 | 2×2 | 며칠 남았나 | 없음 | 첫 화면 |
| 다음에 풀 것 | 4×2 | 뭘 풀지 | 없음 | **줄마다** 그 과목 |

### 누르면 그 위젯이 말하던 자리로

푼 것을 보여 주던 넷은 달력으로, 회차를 짚어 주던 '다음에 풀 것'은 **줄마다
그 과목의 목록으로** 갑니다. 갈 데가 마땅치 않은 D-day만 첫 화면입니다. 홈
화면에서 눌렀는데 아무 데나 열리면 위젯을 놓아 둔 값이 절반은 사라집니다.

자리는 주소의 조각(`#cal`, `#/학년/과목/all/all`)으로 건넵니다 — 페이지가 이미
그것으로 화면을 되살리기 때문입니다. 두 군데를 조심해야 합니다.

- **같은 인텐트로 보이면 안 됩니다.** `PendingIntent`는 요청 코드가 같고
  `filterEquals`가 같으면 하나로 칩니다. 추가 정보(extra)는 비교에 안 들어가므로
  조각을 **데이터에도** 실어 둡니다. 그러지 않으면 달력 위젯과 D-day 위젯이
  같은 곳으로 열립니다.
- **달력은 주소가 아닙니다.** 화면 위에 덮이는 것이라, 앱이 이미 떠 있으면
  주소만 바꿔서는 안 열립니다. 그때는 `window.gijulOpenCal()`을 직접 부릅니다.
  과목(`#/…`)은 페이지의 `hashchange`가 받으므로 실어 보내면 됩니다.

### 카드가 크면 글자도 커진다

`sp` 로 못박은 글자는 위젯이 커져도 그대로다. 태블릿에서 4×3 위젯은 폰의 네 배
넓이가 되는데 글자만 그대로라, 카드는 크고 글씨는 좁쌀만 한 꼴이 된다. 안 쓰는
자리가 넓다는 것은 그 위젯이 자리값을 못 하고 있다는 뜻입니다.

`WidgetBase.grow()` 가 기준 크기(4×2 = 250×110dp) 대비 몇 배인지를 내고,
`sp()` 로 글자마다 곱합니다. 가로·세로 중 **덜 자란 쪽**을 따릅니다 — 넓기만
하고 낮은 칸에서 너비에 맞춰 키우면 줄이 겹칩니다. 한 장으로 그리는 위젯은
`fit()` 이 칸 크기에 맞춰 글자를 키웁니다.

줄이 여럿인 위젯은 `spread()` 가 남는 높이를 줄 수만큼 나눠 위아래 여백으로
넣습니다. 세로 막대는 `setViewLayoutWidth/Height`(안드로이드 12부터)로 함께
자랍니다 — 그 아래에서는 고정 크기로 남습니다.

잔디밭만 다릅니다. 칸 크기는 일곱 줄이 정하므로 높이가 결정하고, 그러고 나면
넓은 카드에 너비가 남습니다. 칸을 늘여 채우는 대신 **주를 더 보여** 채웁니다 —
잔디밭이 답하는 질문이 '어디서 끊겼나'라 길수록 낫습니다(15~53주).

### 고르는 화면의 미리보기

`android:previewImage`에 그림을 답니다. **`previewLayout`은 쓰지 않습니다** —
위젯의 내용은 전부 코드가 채우고 레이아웃에는 글자가 하나도 없어서, 그대로
걸면 고르는 화면에 **빈 상자 여섯 개**가 나란히 섭니다. 글자를 박아 넣은 사본을
레이아웃마다 또 만드는 길도 있으나 그러면 같은 그림이 두 벌이 되어 한쪽만
고치는 날이 옵니다.

그림은 `tools/build_widget_previews.py`가 만듭니다. 저장소의
`fonts/GijulSans-*.woff2`를 그대로 쓰므로 미리보기와 진짜가 같은 글꼴입니다.
어두운 쪽은 `drawable-night-nodpi`에 따로 있고 안드로이드가 골라 줍니다.
**위젯의 생김새를 손봤으면 다시 돌립니다.**

    python3 tools/build_widget_previews.py

### 표시를 앱으로 옮겨 적습니다

찍어 둔 것은 **웹뷰 안의 `localStorage`**에 있고 위젯은 다른 프로세스라 거기에
손이 닿지 않습니다. 페이지가 열릴 때마다 통째로 건네주면(`GijulNative.setSolved`)
앱이 `SharedPreferences`에 적고, 위젯은 그것만 읽습니다.

숨길 수 없는 결과가 하나 따라옵니다 — **페이지를 한 번은 열어야** 위젯이 최신이
됩니다. 웹에서만 찍은 것은 앱을 열기 전까지 위젯에 안 보입니다.

위젯용 꾸러미에는 표시 외에 **과목 이름**과 **다음에 풀 것**을 넣습니다. 과목 이름은 열쇠에 과목
번호만 있고 이름표가 페이지에만 있어서고, **다음에 풀 것**은 무엇이 안 풀렸는지
알려면 회차 목록 전부와 내 과목과 표시가 다 있어야 해서입니다. 앱이 알아내려면
자료를 받아 와야 하므로 페이지가 계산해 전달합니다. 같은 `setSolved` 꾸러미에는
복구·백업에 필요한 `favs`·`theme`·`times`·`records`도 함께 담습니다.
같은 계정의 다른 기기 기록도 앱 페이지가 수신한 뒤 위젯 사본에 반영합니다.

### RemoteViews 가 펼 수 있는 뷰만 쓴다

`RemoteViews`는 아무 클래스나 못 편다. `@RemoteView`가 붙은 것만 편다 —
**`android.view.View`에는 안 붙어 있습니다.** 막대를 그리려고 `<View>` 하나를
넣어 두었더니 그 두 벌('최근 푼 것'·'다음에 풀 것')만 홈 화면에서
**"위젯을 추가할 수 없습니다"**가 뜨며 통째로 안 올라갔습니다. 나머지 넷은
`ImageView`·`ProgressBar`만 써서 멀쩡했고요.

`Space`도 마찬가지입니다. 자리를 벌릴 일이 있으면 **글자 없는 `TextView`**를
씁니다. 위젯 레이아웃에 새 뷰를 넣을 때는 그 클래스에 `@RemoteView`가 붙어
있는지부터 봅니다.

### 앱과 같은 글꼴로 그립니다

위젯은 웹뷰가 아니라 안드로이드가 직접 그리므로 `fonts/*.woff2`를 읽지
못합니다. `tools/build_fonts.py`가 웹폰트를 만들면서 같은 글자를 담은 ttf를
`res/font/gijul_500.ttf`·`gijul_700.ttf`로 함께 냅니다. 진짜 글자를 내는 위젯은
레이아웃의 `android:fontFamily`가, 한 장으로 그리는 위젯은 `WidgetBase.font()`가
씁니다 — 한 위젯 안에서 두 글꼴이 섞이면 그림 부분만 남의 앱처럼 보입니다.

원본을 따로 자르지 않고 웹폰트를 그대로 푸는 것은, 두 벌이 서로 어긋날 자리를
만들지 않기 위해서입니다. **웹에 없는 글자는 위젯에도 없어야 맞습니다.**

### 크기를 런처에게 제대로 물어봅니다

런처가 주는 것은 한 크기가 아니라 넷입니다 — `MIN_WIDTH`·`MAX_HEIGHT`가
**세로일 때**의 크기이고 `MAX_WIDTH`·`MIN_HEIGHT`가 **가로일 때**입니다. 짝을
섞어 물으면 세로의 너비에 가로의 높이를 재게 되어, 비율이 어긋난 그림을 늘여
붙입니다. 태블릿을 가로로 두었을 때 글자가 옆으로 늘어나 보이던 것이
이것이었습니다. 안드로이드 12부터는 `OPTION_APPWIDGET_SIZES`로 아예 목록을
주므로 그쪽이 있으면 그것을 씁니다.

그림도 늘여 붙이지 않습니다(`fitCenter`). 비율이 조금 어긋나 옆이 비는 편이
글자가 늘어나는 것보다 낫습니다.

그리고 **글자와 이름표는 칸 크기를 따라 자랍니다**(`WidgetBase.fit`). dp로
못박아 두었더니 칸이 70dp가 넘는 태블릿에서 8.5dp 글자가 구석에 붙어 칸이
통째로 비어 보였습니다.

### 그림을 그리는 위젯과 안 그리는 위젯

`RemoteViews`는 아무 뷰나 못 씁니다. 달력의 격자는 칸이 마흔둘이고 칸마다
이름표가 또 여럿이라 뷰로 내면 수백 개가 되고, 런처에 건네는 꾸러미가 한도를
넘으면 **위젯이 통째로 안 뜹니다**. 그래서 한 장으로 그립니다. 이번 주의 막대도
높이를 그때그때 정해야 하는데 `setViewLayoutHeight`가 안드로이드 12부터라
마찬가지입니다.

대신 그 둘만 **글자 크기가 기기 설정을 안 따릅니다.** 나머지 넷은 진짜 글자와
색칠한 네모뿐이라 따라갑니다. D-day의 비율은 `ProgressBar`가 냅니다 —
RemoteViews가 다룰 수 있는 몇 안 되는 뷰라 그림 없이 비율을 낼 유일한 길입니다.

### 스스로 깨어나지 않습니다

`updatePeriodMillis`는 0입니다. 표시가 바뀌는 것은 페이지를 열었을 때뿐이고
그때 앱이 직접 깨우므로, 30분마다 일어나 같은 그림을 다시 그릴 까닭이 없습니다.

다만 **날은 저절로 바뀝니다.** '오늘'과 D-day와 이번 주가 자정에 어긋나므로
자정 직후에 한 번만 깨우는 알람을 스스로 겁니다. 정확한 알람은 쓰지 않습니다 —
몇 분 늦어도 '오늘'이 하루 어긋나지는 않고, 정확한 쪽은 안드로이드 12부터
따로 권한을 물어야 합니다. 마지막 위젯을 떼면 알람도 거둡니다.

## 뒤로가기

한 번 누르면 **화면에 열어 둔 것 하나가 닫힙니다.** 위에 덮인 것부터입니다 —
크게 보기 → 시트(보내기·받아둔 자료·AI로 쓰기·갱신 내역) → 알림 막대 →
내 과목 편집. 닫을 것이 없으면 방문 기록을 되짚고, 그것도 없을 때에만
**한 번 더 눌러야** 앱이 닫힙니다.

무엇을 닫았는지는 앱이 판단하지 않습니다. 페이지의 `window.gijulBack()`이 하나를
닫고 그 사실을 돌려주며, 앱은 그 답이 거짓일 때만 다음 단계로 갑니다. 화면에
새 겹판을 더할 때는 그 함수에 한 줄을 더하면 됩니다 — 앱은 고치지 않아도 됩니다.

닫는 동작은 **종료 수를 세지 않습니다.** 무언가 닫혔거나 기록을 되짚었으면 '한 번
더' 대기가 풀립니다. 그러지 않으면 시트를 닫은 다음 누른 뒤로가기가 곧장 종료로
이어져, 닫는 동작이 종료의 첫 번째 누름을 대신하는 꼴이 됩니다.

알림 막대는 **답 없이 거둡니다.** 뒤로가기는 '지금은 됐다'는 뜻이지 '아니오'가
아니어서, '아니오'로 처리하면 앱 설치 권유를 뒤로가기로 넘긴 사람에게 다시는
묻지 않게 됩니다.

## 밖에서 받아 오는 길

받는 자리가 셋입니다 — 문제지(EBSi), 회차 목록(우리 사이트), 새 판 APK(릴리스).
셋 다 `Net.open(주소, 허용목록)` 을 지납니다.

**리디렉션을 한 발씩 딛습니다.** 예전에는 세 곳 모두 주소를 한 번 확인하고
`setInstanceFollowRedirects(true)` 로 두었습니다. 302 를 만나면 묻지 않고 따라
가므로, 허용된 서버에 리디렉션 하나만 열려 있으면 그 목록은 통째로 무의미해집니다.
HTTPS 라 도청은 막히지만 **어디서 받아 왔는지를 우리가 모르게 되는 것**이 요점
입니다. 지금은 매 홉마다 다시 봅니다(최대 5홉).

릴리스 자산은 `github.com` 이 실제 파일이 있는 곳으로 한 번 넘기는데, **그 자리
이름을 깃허브가 조용히 바꿉니다** — 예전에는 `objects.githubusercontent.com`,
지금은 `release-assets.githubusercontent.com` 입니다. 그래서 하나를 못박지 않고
`*.githubusercontent.com` 을 받습니다. 못박아 두었으면 이름이 바뀐 날 모두의 자동
갱신이 조용히 멈췄을 것입니다.

## 웹뷰에 열어 둔 것

창구(`GijulNative`)가 붙어 있는 웹뷰입니다. 여는 것은 우리 사이트뿐이고 그 밖은
`shouldOverrideUrlLoading` 이 넘기지만, **열 수 있는 것을 좁혀 두는 일과 열지
않기로 하는 일은 다릅니다.** `file://`·`content://`·위치정보·혼합 콘텐츠를 모두
명시적으로 닫습니다 — 앞의 둘은 안드로이드 10 아래에서 기본이 켜짐입니다.

## 개인 자료를 지키는 층

앱이 지는 몫이 둘 있습니다. 전체 그림은
[docs/build.md](build.md#개인-자료를-지키는-층)에 있습니다.

**앱 안의 사본.** 페이지가 표시를 건넬 때마다 `SharedPreferences`에 적습니다.
원래는 위젯이 읽으려고 둔 것인데, 웹뷰의 자료가 날아가도 이쪽은 남습니다. 그래서
페이지가 뜰 때 **화면은 비었는데 사본에 있으면** 되살릴지 묻습니다
(`GijulNative.savedSolved`). 백업을 안 해 둔 사람에게 남는 마지막 줄입니다.
돌려줄 때는 백업 파일과 **같은 모양**으로 맞춥니다 — 무엇이 맞는 백업인지는
페이지가 알아야 하고, 여기서 또 보면 규칙이 두 벌이 됩니다.

**백업 파일 내보내기·가져오기.** 웹에서는 `<a download>` 한 줄이면 되는데
웹뷰에서는 아무 일도 일어나지 않습니다 — 내려받기를 받아 줄 것이 붙어 있지
않아서입니다. 그런데 **백업이 가장 절실한 쪽이 앱 사용자**입니다(브라우저와 달리
앱을 지우면 통째로 사라집니다). 그래서 창구로 받습니다.

| 창구 | 하는 일 |
|---|---|
| `saveBackup(json, name)` | 캐시에 쓰고 **공유 시트**를 띄웁니다 |
| `pickBackup()` | SAF 파일 고르기 → `onActivityResult` 가 읽어 페이지로 |
| `savedSolved()` | 앱이 들고 있는 사본을 백업 모양으로 |
| `pickAutoBackup()` | 자동으로 쓸 자리를 한 번 고릅니다 |
| `autoBackup()` | 지금 어디에 쓰고 있는지 · 막혔는지 |
| `stopAutoBackup()` | 그만두고 권한도 놓습니다 |

### 구형 SAF 자동 백업

Google 계정에 연결하지 않은 앱의 기존 파일 자동 백업입니다. 새 동기화는 아래
[Google 계정 동기화](#google-계정-동기화)를 사용합니다.

`ACTION_CREATE_DOCUMENT`로 새 문서를 만들거나 `ACTION_OPEN_DOCUMENT`로 기존
문서를 고릅니다. `DocumentAccess`는 반환 Intent가 실제 준 읽기/쓰기 grant와
교집합을 사용합니다. 읽기·쓰기 지속 권한을 확인한 뒤에만 AUTO_URI를 저장하고,
실패하면 오류를 표시합니다. 저장된 URI도 persistedUriPermissions와 대조하여
권한이 없으면 해제하고 다시 선택하도록 안내합니다. Drive 내부 provider URI를
문자열로 만들어 권한을 대신하지 않습니다.

자동 읽기는 앱 실행/복귀와 60초 점검에서 내용을 읽어 SHA-256으로 비교합니다.
LAST_MODIFIED가 없어도 변경을 확인합니다. 쓰기 직전에 다시 읽어 바뀐 파일은
페이지에서 먼저 합칩니다. `BackupIO`가 쓰기 전 정상 사본과 대기 사본을 앱 내부에
남기며 쓰기 뒤 내용을 검증합니다. 빈 기존 파일은 정상 백업으로 취급하지 않습니다.

제공자 문서는 `openOutputStream(uri, "wt")`로 직접 덮어씁니다. 앱 내부 사본의 원자적
저장과 달리 원격 문서 교체·revision 기반 CAS는 구현되어 있지 않습니다. 제공자 오류나
두 기기의 동시 쓰기를 완전히 막지는 못합니다. 실패는 백업 화면에 표시하며,
0바이트 파일을 다시 연결하는 대신 정상 수동 백업 또는 내부 복구 사본을 먼저 확인합니다.

## Android OS 백업 범위

`backup_rules.xml`과 `data_extraction_rules.xml`은 file·external 도메인의 파일을
제외합니다. 받아둔 문제지와 앱 내부 파일 사본은 OS 백업에 기대지 않고, 문제지는
다시 받거나 직접 공유하며 풀이 기록은 계정 동기화·JSON 백업을 함께 사용합니다.
SharedPreferences 등 제외하지 않은 앱 데이터도 실제 백업·복원 여부는 OS 설정과
기기에 의존합니다. 웹뷰 기록이 반드시 기기 변경 시 복원된다고 보장하지 않습니다.
Android 12+ 규칙에는 클라우드 백업과 기기 간 전송을 각각 명시합니다.

## 앱 자체 업데이트

껍데기(WebView 바깥의 네이티브 부분)를 고칠 때만 APK가 새로 필요한데, 스토어를
거치지 않으니 알려줄 주체가 없습니다. 그래서 **명세를 사이트에 같이 올려두고 앱이
직접 읽습니다.**

```
app/latest.json        versionCode·versionName·url·size·sha256·notes
```

APK 자체는 저장소가 아니라 **GitHub 릴리스 자산**으로 나갑니다. 판본마다 APK가
히스토리에 영구히 쌓이면 받는 사람 전부가 그 비용을 내기 때문입니다. `android.yml`이
서명해 빌드한 APK를 `versionName`으로 태그를 달아 릴리스에 붙입니다.

```
릴리스에 붙는 이름   gijul-direct.apk           (늘 같습니다)
사람이 누르는 주소   …/releases/latest/download/gijul-direct.apk
latest.json 의 url   …/releases/download/v10.1/gijul-direct.apk
```

아래쪽은 **판본을 못박습니다.** `latest.json`은 한 판본을 가리키는 문서라, 주소만
`latest`로 두면 다음 판이 올라간 순간 거기 적힌 크기·sha256과 실제로 내려오는
파일이 어긋나고 앱이 설치를 거부합니다.

앱은 **실행할 때마다**, 그리고 다시 앞으로 불러올 때마다 이 명세를 보고, 설치된
versionCode보다 크면 알림 막대를 띄웁니다. 누르면 받아서 시스템 설치 화면으로
넘깁니다. 새 버전이 없으면 아무 말도 하지 않습니다 — 그래야 매번 확인해도 됩니다.

설치 화면을 띄우기 **전에** 받은 파일을 직접 열어 세 가지를 확인합니다 — SHA-256이
명세와 같은지, 패키지 이름이 우리 것인지, **서명 인증서가 지금 실행 중인 앱과
같은지.** 세 번째는 안드로이드도 강제하지만 그건 설치 화면이 뜬 뒤의 일이라, 그
앞에서 먼저 거릅니다.

명세에 지문이 **없으면 거기서 멈춥니다.** 예전에는 없으면 그 검사를 건너뛰었는데,
지문을 적는 것도 명세라서 명세를 갈아치울 수 있는 쪽이 그 한 줄만 빼면 검사를
통째로 끌 수 있었습니다. 서명 확인이 마지막 문이지만, 문을 하나 열어 두고 다음
문을 믿을 까닭이 없습니다. 그래서 **서명 키가 바뀌면 기기가 업데이트를 거부합니다.**

안드로이드 8+에서는 이 앱에 "이 출처 허용"을 한 번 줘야 하며, 없으면 앱이 해당
설정 화면으로 안내합니다.

## 새 판본 내보내기

`android/app/build.gradle`의 `versionCode`와 `versionName`을 올려 main에 밀면
끝입니다. 나머지는 `android.yml`이 합니다 — 시크릿의 키로 서명해 빌드하고,
**지문이 이전 판본과 같은지 확인하고**, 릴리스를 만들어 APK를 붙이고,
`app/latest.json`을 커밋합니다.

차례가 정해져 있습니다. **릴리스를 먼저 만들고 명세를 나중에 커밋합니다** —
반대로 하면 명세가 아직 없는 주소를 가리키는 동안 앱이 그것을 읽고 내려받기에
실패합니다. versionCode가 늘지 않았으면 거기서 조용히 멈춥니다.

사용자의 알림 막대에 뜰 한 줄은 **커밋 본문의 `Notes:` 줄**에서 가져옵니다.

```
Release 10.2

Notes: 문제지를 넘길 때 쪽 번호를 함께 보냅니다
```

그 줄이 없으면 "앱을 새로 고쳤습니다"로 갑니다. 커밋 제목은 영어 관례라 그것을
쓰면 화면에 "Release 10.2"가 나가므로, 제목을 그대로 가져다 쓰지 않습니다.

손에서 명세만 확인하고 싶다면 `python3 tools/publish_apk.py --notes "…"`가
`app/latest.json`을 써 줍니다. 다만 릴리스 자산을 올리는 것은 워크플로 몫이라,
그것만으로는 배포가 끝나지 않습니다.

### 서명 지문 확인

`android.yml`은 서명한 APK의 인증서를 `docs/assetlinks.json`의 지문과 대조하고,
다르면 **거기서 멈춥니다.** 서명 키가 바뀐 APK는 기존 기기가 영영 거부하므로
(지우고 새로 깔아야 하며 받아둔 자료도 사라집니다), 나가기 전에 막습니다.

## Google 계정 동기화

10.1부터 백업 화면에서 Google 계정을 선택적으로 연결합니다. 웹은 Google 로그인
팝업, Android는 Credential Manager의 ID 토큰을 Firebase Auth로 검증합니다.
구형 APK에 로그인 메서드가 없으면 업데이트를 안내합니다. 현재 서버는
`direct-mogo` 프로젝트의 Standard Firestore, `asia-northeast3` 리전입니다.

같은 계정의 푼 날·풀이시간·점수·틀린 번호·내 과목·테마를 이벤트 단위로 전송합니다.
PDF 보관함은 동기화하지 않습니다. 오프라인 변경은 IndexedDB에 남고 서버가 쓰기를
확인한 뒤 대기를 지웁니다. 충돌·삭제 이력·첫 연결·재전송 계약은 [docs/sync.md](sync.md)를
따릅니다. 파일 백업 가져오기는 기존대로 이 기기 값이 이기는 합치기가 기본입니다.

Google 계정 연결은 `setCloudSyncActive(true)`로 구형 SAF 자동 읽기·쓰기를 멈춥니다.
기존 Drive 파일과 복구 사본은 남기고 수동 내보내기/가져오기는 계속 제공합니다.
로그아웃도 로컬 기록·전송 대기를 보존하며 구형 자동 백업을 자동 재개하지 않습니다.
계정 전환·서버 이력 선택 복원·클라우드 기록 삭제 UI는 아직 제공하지 않습니다.

실제 SDK/규칙 에뮬레이터와 Google 웹 로그인 화면 진입, API 36 앱 UI를 확인했습니다.
실제 계정 로그인 완료·두 실제 기기 동기화는 별도 검증 대상입니다. 보관·삭제와
Google Analytics 미사용 정책은 [PRIVACY.md](../PRIVACY.md)에 있습니다.

## 실시간 정보가 안 뜰 때

재는 동안의 알림은 **실시간 정보**로 올려 달라고 청합니다(`android.requestPromotedOngoing`).
그래야 잠금화면의 나우바와 상태 표시줄에 남은 시간이 뜹니다. **청하는 것이라 조용히
거절당합니다** — 그러면 사용자에게는 그냥 안 되는 것으로 보입니다.

그래서 조작판(⏱ 아이콘 → 팝업)이 왜 안 되는지 한 줄로 말합니다.

| 뜨는 말 | 뜻 | 할 수 있는 것 |
|---|---|---|
| 잠금화면에 뜨고 있습니다 | 깃발이 붙었습니다 | — |
| 안드로이드 16부터 됩니다 | 기기가 15 이하 | 없습니다. 창구 자체가 없습니다 |
| 알림이 꺼져 있습니다 | 알림 권한 없음 | 알림을 켭니다 |
| 잠금화면에 안 뜹니다 — 눌러서 설정 열기 | 조건은 갖췄는데 깃발이 안 붙었습니다 | 누르면 설정으로 갑니다 |

**되고 있을 때도 한 줄 남깁니다.** 안 뜨는데 아무 말도 없으면 어디를 봐야 할지조차
모릅니다. 그 아래에 판단의 근거를 그대로 내보입니다 —
`SDK 36 · 알림 O · 허용 O · 등급 3 · 승격 X` 처럼. 짐작으로 주고받는 것보다 이
한 줄이 빠릅니다(`Timing.liveWhy()`).

**한 번 물렸습니다.** 못 찾았을 때를 '켜진 것'으로 쳤더니, 안 되는데 안 된다는
말조차 안 나왔습니다. 모르는 것은 모른다고 해야 합니다.

### 채널 등급이 낮으면 올릴 자리가 없습니다

처음에는 `IMPORTANCE_LOW` 였습니다. 독서실에서 갑자기 울리면 곤란해서 고른
등급인데, **그 등급은 상태 표시줄에 아이콘이 아예 안 뜹니다.** 승격은 본디 상태
표시줄과 잠금화면에 올리는 일이라 올릴 자리가 없으면 조용히 안 됩니다.

그래서 `IMPORTANCE_DEFAULT` 로 올리되 **소리와 진동은 손으로 껐습니다**
(`setSound(null, null)` · `enableVibration(false)`). 조용한 것은 그대로이고
자리만 생깁니다.

**채널 이름을 새로 냈습니다**(`timer` → `timer.v2`). 한 번 만든 채널의 등급은
코드로 못 바꿉니다 — 옛 이름 그대로 두면 낮은 등급이 영원히 남습니다.
옛 채널은 지웁니다.

### 안드로이드는 올렸는데 나우바에 안 뜰 때

**One UI 8 은 남의 앱의 라이브 알림을 개발자 옵션 뒤에 두었습니다** —
`Live notifications for all apps`(모든 앱의 라이브 알림). 그것이 꺼져 있으면
프레임워크가 `FLAG_PROMOTED_ONGOING` 을 붙여도 **나우바에는 삼성 제 앱만
올라갑니다.**

실제로 이 저장소에서 그 상태를 만났습니다. 조작판의 근거 줄이
`SDK 36 · 알림 O · 허용 O · 등급 3 · 승격 O` 인데도 나우바에 안 떴습니다 —
앱이 할 수 있는 것을 다 한 자리입니다.

자리는 여기입니다 — **개발자 옵션 → 맨 아래 추가 설정 → 모든 앱의 라이브 알림.**
스스로 찾아갈 만한 자리가 아닙니다.

**그 스위치의 상태는 앱에서 읽을 수 없습니다.** 그래서 단정하지 않고 길만 엽니다.

- **처음 시간을 재는 한 번**에만 시트로 묻습니다(`offerLive`). 뜰 때마다 물으면
  광고가 되고, 그 순간이 이 기능이 무엇에 쓰이는지 가장 잘 보이는 때입니다.
  알림 권한을 먼저 묻고 그 뒤에 폅니다 — 창 둘이 겹치면 뒤엣것이 앞엣것을
  지우고 앉습니다.
- 그 뒤로는 조작판 줄에만 남습니다 — '올렸습니다 — 나우바에 안 보이면 눌러
  주십시오'.

개발자 옵션 자체가 없으면 설정 → 휴대전화 정보 → 소프트웨어 정보에서 빌드 번호를
일곱 번 눌러 켭니다. 시트가 그 줄도 함께 적습니다.

### 알약의 숫자가 굳는 자리

`setShortCriticalText` 는 **정적입니다.** 다시 띄우기 전까지 그 글자에 굳는데,
우리는 상태가 바뀔 때만 다시 띄우므로 시계가 멈춰 보입니다.

비워 두면 시스템이 **크로노미터로 스스로 셉니다** — 그래야 초까지 흐릅니다.
다만 크로노미터는 값이 **양수인 동안만** 쓰이므로, 멈췄거나 시간을 넘긴 뒤에는
값이 실제로 정적이라 그때만 글로 적습니다. `Clock.brief()` 는 그 두 자리에만
쓰입니다.

## 기기 없이 확인하는 것

`android/app/src/test` 에 단위 시험 36개이 있습니다. 평범한 JVM에서 십몇 초면 끝나고,
`android.yml` 이 **빌드 앞에서** 돌립니다 — 서명해서 릴리스까지 낸 다음에 셈이
틀렸다는 것을 알아 봐야 늦습니다.

```bash
cd android && ./gradlew --no-daemon testDebugUnitTest
```

**틀려도 조용히 틀리는 자리만** 골랐습니다. 화면에서는 아무 일도 안 일어나고
오류도 안 나는데 결과만 어긋나는 것들입니다.

| 무엇 | 어긋나면 |
|---|---|
| `Net.EBSI/SITE/RELEASE` | 남의 서버에서 받아 옵니다. 점 하나 차이로 `notebsi.co.kr` 이 통과합니다 |
| `Names.safe()` | 우리 폴더 밖에 파일을 씁니다 |
| `Solved.byDay()` | 위젯 여섯이 전부 이것을 거칩니다. 회차 이름에 `/` 가 들어가면 잘립니다 |
| `Solved.streak()` | 잔디밭과 이번 주의 '며칠째'가 틀립니다 |
| `Clock.brief()` | 상태 표시줄의 짧은 글이 틀립니다. 자리가 손톱만 해서 어긋나도 눈에 안 띕니다 |
| `Exam.minutes()` | **시험 시간이 조용히 틀립니다.** 모르는 이름이 오면 30분으로 떨어지는데, 30분은 탐구의 정상값이라 오류도 로그도 안 남습니다. 실제로 과목 코드가 들어와 모든 과목이 30분이던 적이 있습니다(8.9에서 고침) |
| `Clock.face()`·`record()` | 남은 시간과 회차에 남는 기록이 어긋납니다 |

**못 보는 것이 더 많습니다.** 위젯이 실제로 그려지는 모습, SAF, 웹뷰, 띄운 창은
기기가 있어야 하고 이 시험이 그것을 대신하지 않습니다. 여기 있는 것은 답이
정해진 셈뿐입니다.

### 그러자면 셈을 밖으로 꺼내야 했습니다

`safe()` 는 `MainActivity` 안에 있었습니다. `Activity` 를 상속한 클래스라
불러오는 것만으로 안드로이드 틀이 딸려 와서, 기기 없이는 값을 넣어 볼 수가
없었습니다. `Names` 로 옮겼습니다.

`Net.Allow` 는 `android.net.Uri` 를 받았습니다. 셈은 안드로이드와 아무 상관이
없는데 그 그릇 때문에 묶여 있던 것이라, **호스트 글자**를 받게 했습니다.

`Solved.byDay()`·`backup()` 은 `Context` 로 읽어 오는 자리와 **적힌 글자를 읽는
자리**를 나눴습니다. 뒤쪽만 시험합니다.

셋 다 코드가 오히려 짧아졌습니다. 확인할 수 있게 만드는 일과 정리하는 일이
같은 방향이었습니다.

## 빌드

Actions의 **APK 빌드** 워크플로를 수동 실행하면 artifact로 받을 수 있습니다.
직접 빌드하려면:

```bash
cd android
echo "sdk.dir=$ANDROID_HOME" > local.properties
./gradlew --no-daemon testDebugUnitTest lintDebug assembleDebug
# app/build/outputs/apk/debug/app-debug.apk
```

설치할 때 "출처를 알 수 없는 앱"을 허용해야 합니다.

## 릴리스 서명

이 프로젝트는 **GitHub Actions의 기존 릴리스 서명 키**를 사용합니다. 시크릿
`KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD`가 등록되어
있다는 작업 전제를 유지합니다. 새 키를 만들거나 기존 키·비밀번호를 로컬로 받아
추출하지 않습니다. 로컬에서는 저장소 Wrapper로 디버그 빌드·시험을 수행합니다.

서명 APK만 필요하면 원하는 커밋을 원격 작업 브랜치에 올리고 그 브랜치에서
`android.yml`을 수동 실행하여 `gijul-direct-apk` artifact를 받습니다. 실제 앱 업데이트는
versionCode +1, versionName 판올림, 한국어 `Notes:`를 준비하고 main으로 발행합니다.
현재 앱은 10.1 / 92이고 다음 네이티브 판본은 10.2 / 93입니다. 문서·웹만 고치면
main의 Pages 배포를 확인하며 APK 판올림은 하지 않습니다.

완료 판정은 워크플로 성공에 더해 `assembleRelease`·`서명 확인` 단계가 실행되고
결과 APK 인증서가 기존 SHA-256
`54370ed90c11e53dbc7d3cc05558f49dd111bd6578e433850d6e83622cfd10c1`과 같은 것입니다.
시크릿 부재로 디버그 빌드에 fallback한 실행은 릴리스 서명 성공이 아닙니다.
실제 인증·시크릿 오류는 보고하며 매 작업마다 키 제공을 다시 요청하지 않습니다.

서명 키를 바꾸면 기존 앱에 업데이트할 수 없고 자체 업데이트도 거부합니다.
기존 지문·Wrapper SHA-256·의존성 검증·서명 확인 단계를 유지합니다.

## 링크를 앱으로 받기

앱이 사이트 주소를 받도록 등록해 두었습니다(`AndroidManifest.xml`의 VIEW 인텐트 필터).
그런데 **안드로이드가 그 등록을 인정하려면 도메인 뿌리에 확인 파일이 있어야 합니다.**

```
https://mangom72.github.io/.well-known/assetlinks.json
```

경로가 아니라 **뿌리**입니다. 이 저장소는 프로젝트 페이지라 `/Direct-mogo/` 아래에만
파일을 놓을 수 있어서, 저 자리는 **사용자 페이지 저장소**의 몫입니다.

### 한 번만 하면 되는 절차

**1. `mangom72/mangom72.github.io` 저장소가 있는지 확인합니다.**
   없으면 새로 만듭니다 — 이름이 정확히 `mangom72.github.io`여야 사용자 페이지가 됩니다.
   Public, README 하나로 시작해도 됩니다.

**2. 그 저장소에 파일을 놓습니다.** 경로와 이름이 정확해야 합니다.

```
mangom72.github.io/
  .well-known/
    assetlinks.json      ← 이 저장소의 docs/assetlinks.json 을 그대로 복사
```

내용은 [`assetlinks.json`](assetlinks.json)에 서명 지문까지 채워 두었습니다.
`.well-known` 앞의 점을 빠뜨리지 마세요.

**3. Pages를 켭니다.** Settings → Pages → Source를 `main` / `/ (root)`로.
   사용자 페이지는 보통 자동으로 켜집니다.

**4. 실제로 내려오는지 봅니다.** 이게 안 되면 아래는 전부 무의미합니다.

```bash
curl -i https://mangom72.github.io/.well-known/assetlinks.json
```

`200`과 JSON 본문이 나와야 합니다. `404`면 경로나 Pages 설정이 틀린 것입니다.
`Content-Type`은 `application/json`이 아니어도 동작합니다.

**5. 기기에서 다시 확인시킵니다.** 앱을 새로 설치하면 자동으로 수행되지만, 이미 설치되어 있는 경우에는:

```bash
adb shell pm verify-app-links --re-verify kr.gijul.direct
adb shell pm get-app-links kr.gijul.direct
```

마지막 줄이 `mangom72.github.io: verified` 로 바뀌면 끝입니다.
`none`이나 `1024`(확인 실패)면 4번이 제대로 안 된 것입니다.

### 확인이 안 돼도 쓸 수 있습니다

**설정 → 앱 → 기출 직행 → 기본으로 열기 → 지원되는 링크 열기**를 켜면
확인 없이도 링크가 앱으로 갑니다. 기기마다 한 번씩 해야 합니다.

페이지 쪽에도 길이 있습니다. 안드로이드 브라우저로 열면 각주에 **앱으로 열기**가
나타나고, 누르면 `intent:`로 앱을 두드립니다 — 깔려 있으면 열리고, 없으면 APK
내려받기로 갑니다.

**페이지가 스스로 넘기지는 않습니다.** 예전에는 안드로이드로 보이면 곧장 `intent:`로
이동했는데, UA에 Android를 달고 오면서 `intent:`는 다룰 줄 모르는 것들이 있었습니다 —
검색엔진의 렌더러와 성능 측정 도구가 그렇습니다. 이동하려는 순간 문서가 통째로
사라져 `document.body`조차 남지 않았고, 빈 화면이 색인되고 측정은 '한 번도 그리지
않았다'로 끝났습니다. UA로 크롤러만 골라내는 길도 있지만 이름을 대지 않는 크롤러는
못 거르고, 무엇보다 사람과 기계에 다르게 굴 이유가 없어 그러지 않았습니다.
밖에서 온 링크는 App Links가 이미 브라우저를 거치지 않고 앱을 엽니다.

### 기존 서명 확인

`assetlinks.json`과 릴리스 APK의 지문은 기존 값으로 유지합니다. APK 인증서는
다음과 같이 확인하며 앱 링크의 도메인 확인과 업데이트 서명을 함께 검증합니다:

```bash
apksigner verify --print-certs app/build/outputs/apk/release/app-release.apk
```

## 답안지 문서 스캔 (10.2)

풀이 기록의 답안 입력·채점에서 직접 마킹과 사진 읽기를 고른다. 새
`OmrScanner`는 ML Kit document-scanner 16.0.0의 BASE 모드로 한 페이지를
자르고 회전한다. 사진 선택은 ACTION_OPEN_DOCUMENT의 일시적 grant로 읽으며
이 URI를 AUTO_URI에 저장하거나 영구권한을 요청하지 않는다. JPEG를 샘플링·축소한
뒤 요청 ID와 함께 웹에 전달한다. 과거 요청·종료 후 콜백은 무시한다.
이미지는 서버·백업에 보내지 않는다. 상세한 [지원 양식과 검증 범위](omr.md)를 따른다.

API 36 에뮬레이터의 `OmrCheck`는 실제 WebView의 공개 견본 입력·새 스캔 브리지
존재·뒤로가기·늦은 응답 무시를 점검한다. 실물 카메라 촬영 정확도 검증은 아니다.
테스트 fixture를 타깃 앱 `files/omr-fixture`에 넣고
`./gradlew -PgijulRunner=kr.gijul.direct.OmrCheck assembleDebugAndroidTest` 후
`adb shell am instrument -w kr.gijul.direct.test/kr.gijul.direct.OmrCheck`로 실행한다.

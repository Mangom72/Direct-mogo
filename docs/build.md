# 만드는 쪽

웹은 Node 번들러 없이 GitHub Pages의 정적 파일로 제공합니다. 선택적인 Google 계정
동기화에는 Firebase Authentication/Cloud Firestore를 사용합니다. 기준은 2026-10-03,
앱 10.1(versionCode 92)입니다. 실제 설정이 바뀌면 날짜와 함께 다시 대조합니다.

| 파일 | 역할 |
|---|---|
| `index.html` | 앱 전체. 자료 5천여 회차가 gzip+base64로 안에 들어 있습니다 |
| `sw.js` | 서비스 워커. 앱 셸·글꼴·동기화 스크립트·받아둔 PDF를 캐시합니다 |
| `sync/` | 계정 동기화·IndexedDB 저널·고정 Firebase SDK·설정·보안 규칙 ([동기화 안내](sync.md)) |
| `PRIVACY.md` | 로컬 기록·선택적 계정 동기화의 정보 처리·보관·삭제 안내 |
| `data/`, `llms.txt`, `llms-full.txt` | AI·프로그램용 정적 JSON과 사용 안내 |
| `s/`, `sitemap.xml` | 검색엔진과 사람이 읽는 과목별 정적 페이지 |
| `robots.txt` | 크롤러 안내 ([아래](#robotstxt는-이-저장소에서-효력이-없습니다) 참고) |
| `fonts/` | 화면에 나오는 글자만 담은 웹폰트 |
| `tools/refresh_data.py` | EBSi에서 새 회차를 긁어 페이로드를 갱신합니다 |
| `tools/build_api.py` | 페이로드를 `data/` JSON과 `llms.txt`로 내보냅니다 |
| `tools/build_pages.py` | `data/`를 `s/` 정적 페이지와 `sitemap.xml`로 내보냅니다 |
| `tools/build_fonts.py` | 저장소 안의 글자를 모아 웹폰트를 잘라 만듭니다 |
| `tools/check_fresh.py` | EBSi가 새 회차를 아직 올리고 있는지 — 수능 하나로 봅니다 |
| `tools/check_csp.py` | 인라인 스크립트 해시가 CSP와 맞는지 봅니다 |
| `tools/publish_apk.py` | 빌드된 릴리스 APK를 읽어 `app/latest.json`을 씁니다 |
| `tests/` | 회귀 시험 40종 ([tests/README.md](../tests/README.md)) |
| `android/` | WebView 앱 ([docs/android.md](android.md)) |
| — | 무엇이 웹이고 무엇이 앱인지: [docs/split.md](split.md) |
| — | 그것을 iOS로 옮길 수 있는지: [docs/ios.md](ios.md) |
| `.github/workflows/refresh-data.yml` | 매일 15시 23분·23시 23분(KST) 자료 갱신 |
| `.github/workflows/tests.yml` | 화면이나 워크플로를 고쳐 main에 밀면 40종을 돌립니다 |
| `.github/workflows/android-checks.yml` | Android PR에서 단위 시험·lint·디버그 빌드를 확인합니다 |
| `.github/workflows/android.yml` | APK 빌드·서명·릴리스 (main 푸시·수동 실행) |

자료를 `index.html` 안에 넣어둔 덕분에 **이 파일 하나만 캐시하면 조회·필터가
네트워크 없이 전부 동작합니다.** 셸에는 글꼴과 자체 동기화 스크립트도 포함됩니다.
새 PDF, 자료·앱 갱신 확인, Google 로그인·서버 전송에는 네트워크가 필요합니다.

PDF는 EBSi가 `Access-Control-Allow-Origin: *`를 주기 때문에 페이지가 직접 받아
`navigator.share()`로 넘길 수 있습니다. 그래서 설치형 앱에서도 노트앱으로 보내집니다.

## 무엇을 밀면 무엇이 도는가

푸시 검증은 main을 대상으로 하며 웹/Android 검증은 해당 경로의 PR에서도 실행합니다.
수동 실행은 선택한 브랜치에서 가능하지만 Android 릴리스 발행은 main에서만 수행합니다.

| 바꾼 것 | 도는 것 | 하는 일 |
|---|---|---|
| `index.html`·`sw.js`·`sync/`·`s/`·`fonts/`·`tools/`·`tests/`·`requirements/`·`.github/workflows/` | `tests.yml` | 회귀 시험 40종. 실패하면 그때의 화면 그림을 artifact로 남깁니다 |
| Android 관련 PR | `android-checks.yml` | 글꼴 규칙·단위 시험·lint·디버그 APK를 합치기 전에 확인합니다 |
| `android/**` | `android.yml` | 서명 빌드 → **지문 확인** → 릴리스 생성 → APK 첨부 → 글꼴 다시 만들기 → `app/latest.json`·`fonts/` 커밋 |
| (매일 15:23·23:23 KST) | `refresh-data.yml` | EBSi에서 새 회차 수집 → JSON·과목 페이지·글꼴 → `test_fields`·`test_refresh`·`test_stable` → 커밋 → 수능 날짜 대조 → 예약 유지 |

`refresh-data.yml`이 `index.html`을 커밋하므로, 새 자료가 있는 날에는 그 커밋이
이어서 `tests.yml`을 깨웁니다. 자료가 없는 날은 아무것도 커밋하지 않아 조용합니다.

웹·문서는 main 반영 뒤 GitHub Pages의 배포 실행이 성공했는지 확인합니다.
다만 서비스 워커가 셸을 쥐고 있어, 사용자 화면에는 **다음 실행**에 반영되며
그때 "새 자료가 있습니다" 알림이 뜹니다.

### 사람이 보지 않아도 도는 것

이 저장소는 오래 방치되는 것을 전제로 합니다. 그래서 **우리가 아무것도 바꾸지
않았는데 밖이 바뀌어 멈추는 길**을 두 군데 막아 두었습니다.

**빌드 도구와 받은 바이트를 못박았습니다.** 저장소의 Wrapper가 Gradle 9.6.1과
배포 ZIP의 SHA-256을 고정하고, `gradle/verification-metadata.xml`이 AGP 9.4.0과
AndroidX를 포함한 의존성 파일의 지문을 확인합니다. 러너 이미지나 저장소 응답이
우리 모르게 바뀌어도 그대로 빌드에 섞이지 않습니다. 로컬과 CI 모두 `./gradlew`를
써야 같은 관문을 지납니다.

Android 앱은 현재 targetSdk 36, compileSdk 37입니다. 강제 edge-to-edge는 시스템 바 inset으로 처리하고, 뒤로가기는
`OnBackPressedDispatcher`로 받아 Android 16의 예측형 뒤로가기 변경에도 기능이
끊기지 않게 했습니다.

**예약이 꺼지지 않게 지킵니다.** 공개 저장소의 예약 워크플로는 저장소에 60일
동안 아무 일도 없으면 깃허브가 자동으로 끕니다. 워크플로가 돈 것은 활동으로 치지
않습니다. 그런데 이 저장소는 **새 자료가 없는 날 아무것도 커밋하지 않도록** 일부러
만들어져 있고, 시험이 없는 겨울(11월 수능 뒤 ~ 3월 학평 전)이 60일보다 깁니다.
그대로 두면 봄에 조용히 멈춘 채로 새 학년도를 맞습니다. 그래서 갱신 작업 끝에서
마지막 커밋이 50일보다 오래됐으면 빈 커밋 하나로 시계를 되감습니다. 자료가 도는
철에는 한 번도 걸리지 않고, 겨울에도 두어 번입니다.

예약 자체가 시작되지 않은 날은 그 안의 코드로 감지할 수 없습니다. 저장소 시크릿
`HEARTBEAT_URL`을 넣으면 성공한 실행 끝에 외부 감시 서비스로 신호를 보냅니다.
서비스에서는 하루 동안 신호가 없을 때 알리도록 설정합니다. 시크릿이 비어 있으면
워크플로는 종전처럼 동작하고 외부 감시만 꺼져 있습니다.

### GitHub 연결 확인

세션별 프록시·인증 오류를 영구 규칙으로 만들지 않습니다. 현재 환경에서
`git ls-remote origin`과 `gh`의 읽기 연결을 확인하고 필요한 기존 push·Actions 경로를
사용합니다. 토큰·서명 키·비밀번호를 로그나 커밋에 남기지 않습니다.

## 자료 갱신

새 회차는 워크플로가 알아서 채웁니다. 직접 돌리려면:

```bash
pip install -r requirements/refresh.txt -r requirements/fonts.txt
python3 tools/refresh_data.py --dry-run   # 무엇이 늘어나는지만 확인
python3 tools/refresh_data.py             # index.html 갱신
python3 tools/build_api.py                # → data/, llms.txt
python3 tools/build_pages.py              # → s/, sitemap.xml
python3 tools/build_fonts.py              # → fonts/
```

**순서가 있습니다.** `build_fonts.py`는 화면에 실제로 나오는 글자만 담으므로 맨
나중에 돌아야 새 회차 제목과 새 과목 페이지의 글자를 함께 봅니다. 빠뜨리면 그
글자가 네모(□)로 보입니다. `python3 tools/build_fonts.py --check`가 망 없이
확인만 해 줍니다. 워크플로도 같은 순서로 돕니다.

다만 `--check`는 **자기가 모은 목록과 비교할 뿐입니다.** 글자를 모으는 규칙 자체가
잘못되면(주석을 걷어내는 부분이 지나치게 걷는 경우가 그렇습니다) 스스로를 통과시킵니다.
그 규칙을 손볼 때는 `python3 tests/run.py glyphs`로 확인하십시오 — 화면에 실제로
그려지는 글자를 모아 견줍니다.

## 고치고 나면

```bash
python3 tests/run.py        # 회귀 시험 40종, 3분 남짓
```

무엇을 지키는 시험인지는 [tests/README.md](../tests/README.md)에 있습니다.
`index.html`·`sw.js`·`sync/`·`manifest.webmanifest`·`s/`·`fonts/`·`tools/`·
`tests/`·`requirements/`·`.github/workflows/`가 바뀐 채로 main에 올라가면 같은 40종이
CI에서도 한 번 더 돕니다. 실패하면 그때의 화면 그림이 artifact로 남습니다.

기존 기록의 **있는 값은 고치지 않습니다.** 새 시행일을 덧붙이고, 이미 있는 회차는
**비어 있던 칸만** 뒤늦게 채웁니다. 수집량이 기존의 80%에 못 미치면 EBSi 구조가
바뀐 것으로 보고 파일을 건드리지 않은 채 실패합니다.

### 왜 하루 두 번이고, 왜 15시대와 23시대인가

EBSi가 한 회차를 한 번에 올리지 않습니다. 파일 헤더(`Last-Modified`)로 재보면
시행일 0시 기준으로:

| | 빠르면 | 늦으면 |
|---|---|---|
| 정답 | +11시간 | +18시간 |
| 문제 | +9시간 | **+6일** |
| 해설 (평가원) | +25시간 | **+4.7일** |

정답과 문제는 대개 **시행 당일 저녁**에 올라오므로 23시대에 보면 그날 시험이 그날
안에 실립니다. 하지만 파일이 먼저 올라온 뒤 EBSi 기출 목록에는 다음 날 오후가
되어서야 나타나는 경우가 실제로 있었습니다. 15시대 실행은 그 목록 반영 지연을
자동으로 보충합니다. 해설도 며칠 걸리는 일이 흔해서, 한 번에 다 잡으려 하지 않고
하루 두 번 보면서 빈칸을 채웁니다(`top_up`). 덧붙이기만 하던 예전 방식으로 돌리면
반쪽만 잡힌 회차의 빈칸이 **영영 빈칸으로** 남습니다.

두 실행은 23분에 시작합니다. GitHub Actions 예약은 정각에 부하가 몰려 늦어질 수
있으므로, 일부러 정각을 피한 것입니다.

새 자료가 없는 날은 페이로드가 그대로이므로 워크플로가 거기서 끝납니다 — 정적
JSON·과목 페이지·글꼴을 다시 만들지 않고, 커밋도 하지 않습니다.

사람이 보지 않는 채로 나가는 커밋이므로, 내보내기 전에 `test_fields`·`test_refresh`·`test_stable`
세 가지를 돌립니다. 브라우저도 서버도 쓰지 않아 몇 초면 끝나고, 이 작업이 실제로
낼 수 있는 잘못(회차 이름표 겹침, 시험 종류와 출제 기관 어긋남, 학년도 오류, 과목
별칭 충돌, 재현되지 않는 빌드)을 덮습니다. 여기서 실패하면 커밋 단계로 가지 않으므로
자료는 어제 것 그대로 남고, 워크플로가 빨갛게 떠서 사람이 봅니다.

`data/index.json`의 `updated`는 **수록된 가장 최근 시행일**입니다. 돌린 날이
아니므로, 새 회차가 없으면 출력이 바이트 단위로 같고 워크플로도 커밋하지 않습니다.

`index.html`의 인라인 스크립트를 고쳤다면 `python3 tools/check_csp.py --fix`로
CSP 해시를 다시 맞춰야 합니다. 어긋난 채로 나가면 그 스크립트가 통째로 막혀
화면이 껍데기만 남습니다.

## 검색에서 찾아지게

`index.html`은 자료를 압축해 품고 JS로 풉니다. 사람에게는 빠르지만 검색엔진에는
**빈 페이지 한 장**입니다 — 5천여 회차가 통째로 안 보입니다. 그래서 같은 자료를
스크립트 없이 그대로 읽히는 HTML로도 함께 배포합니다.

```
/s/                     과목 색인 77과목
/s/D300/158.html        고3·N수 생명과학Ⅰ 전 회차 (문제·정답·해설 직접 링크)
/sitemap.xml            위 79장
```

회차별 페이지는 만들지 않습니다. 5천여 장이 되는데 한 장에 링크 세 개뿐이라
검색엔진이 알맹이 없는 페이지로 보고 오히려 깎습니다. 과목 페이지 한 장이 그 과목의
링크를 전부 담으므로 잃는 것도 없습니다.

앱 화면과 과목 페이지는 서로 오갑니다. 둘 다 canonical로 자기 자신을 가리켜
중복으로 잡히지 않습니다.

서비스 워커는 **앱 제 주소로 들어오는 이동만** 셸에서 답합니다. 과목 페이지까지
가로채면 첫 방문 때 셸 캐시에 얼어붙어 갱신이 영영 닿지 않습니다.

### 글꼴은 자라므로 다시 물어봐야 합니다

셸은 캐시 우선이라 한 번 받아 두면 다시 묻지 않습니다. 그런데 `fonts/*.woff2`는
**자라는 파일**입니다 — 페이지에 새 글자가 늘 때마다 `build_fonts.py`가 부분집합을
다시 만들어 같은 이름으로 내보냅니다. 그대로 두면 기기에는 처음 깔릴 때의 글꼴이
영영 남고, 그 뒤에 늘어난 글자만 시스템 글꼴로 떨어집니다. 한 제목 안에서 글꼴이
갈리는 꼴이 됩니다 — 달력의 '푼 날'에서 '날'만 딴 글꼴로 나오던 것이 이것입니다.

그래서 `check()`가 문서가 바뀐 것을 확인하면 글꼴도 함께 조건부로 다시 받습니다.
바뀐 것이 없으면 서버가 304만 돌려주므로 값이 거의 들지 않습니다. 기다리지는
않습니다 — 이번 화면은 이미 그려졌고 **다음에 열 때** 제 글꼴로 뜹니다.

### robots.txt는 이 저장소에서 효력이 없습니다

크롤러는 **도메인 뿌리의 robots.txt 하나만** 읽습니다 —
`https://mangom72.github.io/robots.txt`. 여기는 프로젝트 페이지라 이 저장소의
파일이 놓이는 자리는 `/Direct-mogo/robots.txt`이고, 그 주소는 아무도 보지 않습니다.

실제로 효력을 갖는 사본은
[mangom72.github.io](https://github.com/Mangom72/mangom72.github.io) 저장소
뿌리에 있습니다. 이 저장소의 `robots.txt`를 고치면 **그쪽에도 같이 옮겨야
합니다.** 그 저장소는 앱 딥링크용 `.well-known/assetlinks.json`도 같은 방식으로
서비스하고 있습니다.

뿌리의 robots.txt는 그 계정의 **모든 프로젝트 페이지**에 적용됩니다. 다만 내용이
`Allow: /`라 기본 동작과 같으므로 실제로 달라지는 것은 `Sitemap:` 한 줄뿐입니다.

## 로컬에서 보기

```bash
python3 -m http.server 8000
```

서비스 워커는 `localhost`에서도 동작합니다. 캐시 때문에 변경이 안 보이면
개발자도구 → Application → Service Workers에서 Unregister 하세요.

## 브라우저에 남기는 것

화면의 기록은 기존 `localStorage` 형식을 유지합니다. 선택적 계정 동기화는 추가로
IndexedDB에 계정별 변경 저널·전송 대기·확인 기록·수신 체크포인트를 보관합니다.
앱과 브라우저, Safari와 홈 화면 웹 앱의 저장소가 자동으로 공유되는 것은 아닙니다.
같은 Google 계정을 연결하거나 파일 백업으로 옮깁니다.

| 열쇠 | 무엇 |
|---|---|
| `gijul.mysubs.v1` | 내 과목과 순서 |
| `gijul.theme.v1` | 자동 / 밝게 / 어둡게 |
| `gijul.last.v1` · `gijul.pick.v1` | 마지막 조회 조건·고르개 상태 |
| `gijul.solved.v1` | 회차별 푼 날 |
| `gijul.times.v1` | 회차별 `{spent, limit}` 초 단위 풀이시간 |
| `gijul.records.v1` | 회차별 정수 `score`·틀린 번호 배열 `wrong` |
| `gijul.onlyleft.v1` | 안 푼 것만 보기 |
| `gijul.apk.v1` · `gijul.pwa.v1` | 설치 안내 상태 |
| `gijul.bak.v1` | 백업 안내 응답 |
| `gijul.timing-acks.v1` | 네이티브 완료 시간의 중복 전달 방지 ID |
| `gijul.sync.*.v1` | 동기화 설정·계정·변경 의도·화면 복구 이미지·첫 연결 전 사본 |

Firebase 인증 상태는 SDK가 기기에 유지합니다. SDK와 계정 동기화의 저장소는
사이트 데이터 삭제 시 함께 사라질 수 있습니다. 계정·서버 보관 정책은
[PRIVACY.md](../PRIVACY.md)를 따릅니다.

## 개인 자료를 지키는 층

내 과목·푼 날·풀이시간·점수·틀린 번호를 보존합니다. PDF는 별도의 보관함에 있으며
파일 백업과 계정 동기화에는 포함하지 않습니다.

| 수단 | 보존 범위 | 한계 |
|---|---|---|
| localStorage·IndexedDB | 화면 기록·계정에 묶인 전송 대기 | 사이트 데이터 삭제·앱 삭제·저장 공간 부족 |
| 앱 SharedPreferences 사본 | 내 과목·푼 날·시간·점수·오답·테마 | 같은 앱 데이터 안의 사본; 앱 삭제 시 소실 가능 |
| Google 계정 동기화 | 서버가 확인한 변경 이력 | 로그인·통신·규칙 필요; 미전송 대기는 아직 기기에만 있음 |
| 수동 JSON 백업 | 내보낸 시점의 전체 기록 | 이후 변경은 다시 내보내야 함 |
| 구형 SAF 자동 백업·복구 사본 | 파일의 기록·쓰기 전 정상 사본 | Android 전용; 제공자 권한·동시 덮어쓰기 한계 |
| Android OS 백업 | OS 설정과 백업 규칙이 허용한 앱 데이터 | 기기·설정·용량에 의존하며 복원을 보장하지 않음 |

페이지는 `setSolved`로 네이티브 사본을 갱신합니다. 사본의 `Solved.backup()`은 파일
백업과 같은 필드를 포함합니다. 완료된 타이머는 `peekTimings()`로 읽고 JS 저장이
성공한 뒤 `ackTimings(ids)`로 지웁니다. 구형 앱에는 `takeTimings()` fallback이 있습니다.

### 수동 파일 백업

백업 화면에서 내보내기·가져오기를 사용합니다. 앱은 공유 시트/SAF, 웹은 다운로드/
파일 선택을 사용합니다. v1 형식과 기존 열쇠를 유지합니다.

```json
{
  "app": "기출 직행", "v": 1, "at": "2026-10-03T00:00:00.000Z",
  "subs": [{"g":"D300","s":"158"}],
  "solved": {"D300/158/20251113/수능":"20261003"},
  "times": {"D300/158/20251113/수능":{"spent":5520,"limit":6000}},
  "records": {"D300/158/20251113/수능":{"score":84,"wrong":[3,7]}},
  "theme": "auto"
}
```

합치기가 기본이고 같은 항목은 이 기기의 값이 이깁니다. 덮어쓰기는 별도 선택입니다.
판·날짜·값을 검증하며, 모르는 과목의 풀이 기록도 남깁니다. 옛 백업에 `times`나
`records`가 없으면 빈 기록으로 읽습니다. `setSolved`의 `marks`·`subs`·`next` 이름과
기존 인자 수를 유지하고 `favs`·`theme`·`times`·`records`를 함께 전달합니다.

### Google 계정 동기화와 구형 SAF

현재 방식은 [docs/sync.md](sync.md)의 Firebase Auth/Firestore 이벤트 동기화입니다.
서버 확인 뒤 대기를 지우며 서로 다른 회차·항목은 독립적으로 합칩니다. 같은 항목의
동시 편집은 논리 시계·UUID로 판정하므로 **파일 가져오기의 이 기기 우선 규칙과 다릅니다**.
첫 연결 시 기존 클라우드 값·삭제 이력을 우선하고 없는 항목만 기기 기록으로 채웁니다.
연결 전 전체 사본은 `gijul.sync.before.v1`에 남겨 백업 화면에서 복구할 수 있습니다.

계정에 연결한 앱은 구형 SAF 자동 읽기·쓰기를 멈추며 로그아웃해도 자동 재개하지
않습니다. 기존 파일·복구 사본은 삭제하지 않습니다. 연결하지 않은 앱에는 구형
자동 백업이 남아 있으나 권한 소실이나 두 기기의 동시 파일 쓰기를 완전히 해결할
수 없으므로 새 기기 간 동기화에는 같은 Google 계정을 사용합니다.

아직 계정 전환·서버 이력의 버전 선택 복원·클라우드 기록 삭제 UI는 없습니다.
실제 Google 계정 로그인 완료와 두 실제 기기 검증은 별도로 확인해야 합니다.

**줄인 이름은 학년도로 적습니다.** 달력 칸 하나가 100px도 안 되어
`2026학년도 6월 모의평가 · 확률과 통계`가 들어갈 자리가 없습니다. 줄이면
`26 6평 확통`입니다 — 평가원은 **평**(6평·9평), 교육청은 **모**(3모·7모),
학평의 지역은 뗍니다(같은 달의 전국연합은 시행 교육청이 하나뿐입니다).

앞 두 자리는 **둘 다 학년도**(시행 연도 + 1)입니다. 학생이 말하는 `26 3모`가
2025년 3월에 치른 그것이라 줄여 부를 때는 이쪽이 맞습니다. **목록 화면은 지금도
시행 연도로 적으므로**(`2025.03.27`) 두 표기가 한 화면에 섞이지 않도록, 자리가
넉넉한 곳에서는 —달력의 오른쪽 칸, 폰의 아래 목록— 줄이지 않고 그대로 씁니다.

**잰 시간은 표시와 따로 둡니다.** 표시(`gijul.solved.v1`)의 값은 '푼 날' 여덟
자리 하나이고 위젯·백업·달력이 전부 그 꼴을 읽습니다. 거기에 시간을 끼워 넣으면
넷을 한꺼번에 고쳐야 하고 옛 앱은 새 꼴을 못 읽습니다. 열쇠는 같고 통만 다릅니다.

**부호로 적지 않습니다.** 재는 동안에는 `+`가 '넘겼다'는 뜻인데, 끝난 뒤 남기는
값은 (고사 시간 − 소요 시간)이라 양수가 '남겼다'는 뜻이 됩니다. 같은 기호가
반대를 가리키게 되므로 말로 적습니다 — `92분 · 8분 남김` · `108분 · 8분 넘김`.

**홀수형과 짝수형은 한 회차입니다.** 문항 순서만 다른 같은 시험지라, 열쇠에서
떼어 내 둘이 한 열쇠를 씁니다 — 어느 쪽을 찍든 둘 다 찍히고 셈에도 하나로 듭니다.
가형·나형과 A형·B형은 떼지 않습니다. 그쪽은 문제가 서로 다릅니다. 2013년 수능
영어의 'A형 홀수형'처럼 둘이 겹치기도 해서, 홀짝만 골라 뗍니다.

**푼 회차의 열쇠는 `<학년>/<과목>/<시행일>/<회차이름>`입니다.** 넷이 다 필요합니다 —
같은 날 다른 과목이 시행되고, 같은 과목 같은 날에 가형·나형이 따로 있던 해가
있습니다. 값은 참·거짓이 아니라 **푼 날**입니다. '언제 풀었더라'가 다시 풀 때가
됐는지를 정하는 유일한 실마리인데, 참·거짓만 적으면 그것을 영영 잃습니다.

시크릿 모드나 저장소 차단에서는 읽기도 쓰기도 예외가 납니다. 전부 `try`로 감싸
두었고, 실패해도 화면은 그대로 돕니다 — 그 사람에게는 기억만 없을 뿐입니다.

## 종이 OMR 기능 검토·디자인 시안

[종이 OMR 촬영·채점 검토](omr-feasibility.md)와

연결하지 않는다. 연구용 Python 의존성도 `requirements/omr-probe.txt`로 분리했다.

# 앱의 기능을 iOS 웹으로 옮길 수 있는가

안드로이드 앱(`android/`)이 지금 하는 일을 **iOS Safari**와 **홈 화면 웹 앱**이
어디까지 할 수 있는지 하나씩 따져 본 기록입니다. 2026년 8월 기준이고, 판단은
전부 Apple/WebKit 공식 문서와 실제 응답으로 확인한 것만 적었습니다.

등급은 넷입니다.

| | 뜻 |
|---|---|
| **A** | 사실상 똑같이 된다 |
| **B** | 되지만 안드로이드와 다르다 |
| **C** | 다른 방식으로 대신할 수 있다 (열화를 감수한다) |
| **D** | iOS 웹/PWA만으로는 안 된다 |

---

## 지금 어디까지 왔나

이 검토를 마친 뒤 **A로 매긴 것 가운데 웹에 없던 것들을 넣었습니다.**

| 넣은 것 | 어떻게 |
|---|---|
| **웹 보관함** — 회차를 통째로 담고 연결 없이 열기 | Cache Storage, 회차마다 통 하나(`gijul-vault:회차`) |
| **'담김' 표시** | 통 이름만 훑어 대조합니다. 웹에 없던 기능입니다 |
| **받아둔 자료 목록·열기·지우기** | 앱과 같은 화면. 뒤판만 다릅니다 |
| **`Vault` 어댑터** | 앱/웹 두 뒤판, 부르는 쪽은 모릅니다 |
| **홈 화면 웹 앱 권유(iOS)** | 안드로이드 APK 막대와 같은 자리·같은 방식 |
| **저장소 갈라짐 경고** | 사파리 기록이 홈 화면 앱으로 안 따라온다는 안내 |
| `sw.js` — 보관함은 판올림에 안 지워짐 | `sweep()`이 `gijul-vault:`를 건너뜁니다 |

### 기기가 없어도 고를 수 있게 만든 자리

이 저장소에는 iOS 기기가 없고 앞으로도 없을 수 있습니다. 그래서 **판마다 다르게
구는 동작에 사용자를 걸어 두지 않았습니다.**

담아둔 파일을 열 때 브라우저가 blob 을 제 뷰어로 펴 주기를 기대하는데, **iOS
사파리가 PDF blob 을 어떻게 다루는지는 판마다 달랐습니다** — 인라인으로 그린 판도
있고 내려받기로 떨어뜨린 판도 있습니다. 어느 쪽인지 확인하려면 기기가 있어야 합니다.

그래서 확인하는 대신 **갈래를 없앴습니다.** 팝업이 막히면 곧바로 내려받기로
떨어지고, 그와 별개로 '받아둔 자료' 목록에 **내려받기**가 늘 함께 있습니다. 인라인
으로 펴지면 편한 길이 하나 더 있는 것이고, 안 펴지면 원래 있던 길로 갑니다.
**어느 쪽으로 굴러도 파일은 손에 들어옵니다.**

문서에서 온 판단(저장소 갈라짐, 이레 규칙, 위젯 불가)은 기기가 있어도 "확인"할
성질이 아니라 그대로 둡니다. 갈래가 어디서 갈리는지는 `tests/test_tohome.py` 가
UA 를 갈아 끼워 봅니다 — WebKit 의 행동이 아니라 **우리 코드의 판단**을 보는
시험이라 크로미움으로 충분합니다.

## 먼저 — 이번에 확인한 것 하나

**EBSi가 CORS를 열어 두었습니다.** 이것 하나로 이 문서의 절반이 뒤집힙니다.

```
$ curl -sI -r 0-100 https://wdown.ebsi.co.kr/W61001/01exam/20211118/go3/korA_mun_2K1N6P3Q.pdf
HTTP/1.1 206 Partial Content
Content-Type: application/pdf
Access-Control-Allow-Origin: *
Accept-Ranges: bytes
Content-Range: bytes 0-2000/3857002
```

문제지 PDF·정답 PNG 양쪽 다 `Access-Control-Allow-Origin: *` 이고 **바이트 범위
요청도 받습니다.** 그러므로 GitHub Pages에서 띄운 스크립트가 EBSi 문제지를 직접
읽어 화면에 그릴 수 있습니다 — 서버도, 중계도, 프록시도 필요 없습니다.
`connect-src`에 이미 `https://wdown.ebsi.co.kr`가 들어 있으니 CSP도 그대로입니다.

이것이 안 열려 있었다면 자체 뷰어는 **D**였습니다. 지금은 **B**입니다.

**다만 이건 EBSi의 사정이지 우리 것이 아닙니다.** 저쪽이 헤더 한 줄을 지우면 웹
뷰어는 그날로 죽고, 안드로이드 앱은 아무렇지도 않습니다(네이티브 HTTP라 CORS를
안 봅니다). iOS로 가는 계획은 이 한 줄 위에 서 있다는 것을 알고 시작해야 합니다.

## 하나씩

### 1. 자체 PDF/PNG 뷰어 — **B**, 다만 웹에서는 **필요가 없다**

먼저 앞선 판에서 제가 뭉뚱그린 것을 바로잡습니다.

> iOS Safari는 끼워 넣은 PDF를 그림 한 장으로 그려서 첫 쪽만 보입니다.

이 말은 **`<iframe>`·`<embed>`로 끼워 넣었을 때**의 이야기입니다. **링크로 여는
것은 그렇지 않습니다** — 브라우저가 제 뷰어로 열고 쪽을 다 넘깁니다. 그리고 이
사이트는 문제지를 **링크로** 엽니다. 그러니 iOS에서도 이미 됩니다.

그러면 자체 뷰어가 웹에 새로 주는 것은 '우리 화면 안에 머문다' 하나뿐입니다.
값을 재 봤습니다.

| | |
|---|---|
| `pdf.min.mjs` (legacy) | 500 KB |
| `pdf.worker.min.mjs` (legacy) | 1,282 KB |
| `cmaps/` 169개 | 1,140 KB |
| **합계** | **3.0 MB** |

여기에 확대·축소·관성 스크롤·스크롤바·맞춤 토글을 JS로 다시 쓰는 일이 붙습니다.
**브라우저가 이미 잘 하는 일에 3.0 MB와 그만한 코드를 쓰는 것은 값이 안 맞습니다.**
그래서 안 넣습니다.

### 재면서 알게 된 것 — 나중에 다시 재지 않도록

값이 달라져 다시 판단할 날이 오면 이만큼은 이미 알고 있습니다.

- **글꼴은 전부 박혀 있습니다.** 2006~2026년에서 격년으로, 그리고 77과목에서
  44개를 뽑아 훑었더니 임베드되지 않은 글꼴이 하나도 없었습니다. 표준 글꼴
  꾸러미(0.8 MB)는 **필요 없습니다.**
- **cmap 은 두 개만 씁니다** — `UniKS-UTF16-H` 와 `Adobe-Korea1-UCS2`, 합쳐서
  48 KB. 나머지 167개는 44개 표본에서 한 번도 불리지 않았습니다. 다만 당시 전체 5,059회차를
  다 확인한 것은 아니라, 넣는다면 통째로 넣는 편이 안전합니다.
- **cmap 없이는 글자가 깨집니다.** `Identity-H` 는 cmap 이 필요 없지만
  `UniKS-UTF16-H` 는 필요하고, 없으면 한글이 통째로 다른 글자가 됩니다.
- **`legacy` 빌드여야 합니다.** pdf.js 6.2 의 기본 빌드는 `Map.getOrInsertComputed`
  를 쓰는데 이 저장소의 크로미움(Playwright 1194)에 없어 렌더가 통째로 실패합니다.
  옛 사파리를 받아야 하는 우리에게는 어차피 legacy 가 맞습니다.
- **수학 수식은 그림으로는 멀쩡한데 글자로는 안 뽑힙니다.** 수식 글립이 사용자
  정의 영역(U+E000~)에 매핑돼 있어 `getTextContent()` 가 깨진 것처럼 보입니다.
  **렌더링 문제가 아니므로 그것으로 판단하면 안 됩니다.**
- 3.8 MB 짜리 16쪽 문제지의 첫 쪽을 1.6배로 그리는 데 **2.7초**(내려받기 포함)
  걸렸습니다.

### 그래도 할 수 있기는 한가 — 그 표

| | |
|---|---|
| Safari 탭 | 된다 |
| 홈 화면 웹 앱 | 된다 (차이 없음) |
| 필요한 것 | `pdf.js` · Canvas 2D · Web Worker · `fetch` (CORS) |
| 최소 | iOS 11 정도. 최신 pdf.js는 iOS 16.4+ 를 잡는 편이 안전 |
| 권한·제스처 | 없음 |
| 서버 | 필요 없음 |
| GitHub Pages만으로 | **된다** (pdf.js는 정적 파일) |
| 코드 재사용 | Java 0% · UI 설계는 그대로 |

끼워 넣는 길(`<iframe>`·`<embed>`)은 못 씁니다 — iOS 8 이래로 그림 한 장으로
그려서 첫 쪽만 보입니다. 자체 뷰어를 만든다면 `PdfRenderer`가 하던 일을 pdf.js가
대신합니다: 쪽마다 canvas에 그리고 그 canvas를 스크롤 컨테이너에 쌓습니다.
**위에서 적었듯 지금은 안 넣습니다** — 링크로 여는 길이 이미 되기 때문입니다.

**B인 까닭 둘.**
- `PdfViewActivity` 1,652줄 가운데 확대·축소(`ScaleGestureDetector`), 관성 스크롤,
  손수 그린 스크롤바, 맞춤 토글은 전부 JS로 다시 써야 합니다. 옮기는 게 아니라
  새로 만드는 것입니다.
- iOS의 canvas 메모리 한도가 안드로이드 비트맵보다 빡빡합니다. 크게 확대한 큰
  문제지를 통째로 canvas에 올리면 Safari가 탭을 끊습니다. **타일로 나눠 그리는
  것이 선택이 아니라 필수**입니다. `PdfRenderer`는 그런 걱정이 없었습니다.

정답 PNG는 `<img>` 한 줄이라 **A**입니다.

### 2. 오프라인 저장 — **A**(웹 앱) / **B**(Safari 탭)

| | |
|---|---|
| Safari 탭 | 되지만 **7일 만에 지워질 수 있다** |
| 홈 화면 웹 앱 | 된다. 7일 규칙에서 면제 |
| 필요한 것 | Cache Storage (이미 씀) 또는 OPFS |
| 최소 | iOS 11.3 (SW) · OPFS는 Safari 15.2 |
| 권한·제스처 | 없음 |
| 서버 | 필요 없음 |
| GitHub Pages만으로 | 된다 |
| 코드 재사용 | `sw.js`가 **이미 하고 있다** |

`sw.js`의 `cacheFirst(req, FILES, trim)`가 지금도 EBSi PDF를 40개까지 담아 둡니다.
바뀌는 것은 **응답이 더 이상 불투명하지 않다**는 점입니다. CORS가 열려 있으므로
`res.type`이 `"basic"`/`"cors"`가 되고, 그러면

- `caches.match()`로 **담겼는지 물어볼 수 있습니다** → 웹에 없던 '담김' 표시가
  생깁니다. **넣었습니다** — 회차마다 통을 따로 두어(`gijul-vault:회차`) 통 이름만
  훑으면 되므로, 화면을 그릴 때마다 파일을 열어보지 않아도 됩니다.
- 불투명 응답의 **패딩된 용량 계산**을 피합니다. 불투명 응답은 실제 크기와 무관하게
  수 MB씩 할당량을 먹는 구현이 있어, 40개를 담으면 iOS 할당량을 헛되이 태웁니다.

Safari 탭이 B인 까닭: 이레 동안 그 사이트를 안 건드리면 스크립트가 쓴 저장소를
WebKit이 지웁니다. **홈 화면에 추가한 웹 앱은 이 규칙에서 빠집니다.** 그래서 이
기능만큼은 "홈 화면에 추가하세요"가 권유가 아니라 조건입니다.

### 3. 저장소 셋을 어디에 쓰나

기능이 아니라 수단이라 등급을 매기지 않습니다. 무엇을 어디에 둘지는 이렇습니다.

| | 무엇에 | 왜 |
|---|---|---|
| **Cache Storage** | 문제지 PDF·정답 PNG | `Request`/`Response` 그대로 담긴다. 이미 이걸 쓰고 있다 |
| **OPFS** | pdf.js가 범위로 읽어야 할 때 | 워커에서 `createSyncAccessHandle`로 임의 위치 읽기 (Safari 16.4+). 쓰기 스트림은 Safari 26.0 |
| **IndexedDB** | 표시·내 과목·타이머 기록 | **서비스 워커가 읽을 수 있는 유일한 통.** `localStorage`는 워커에 없다 |

지금 페이지는 기록을 전부 `localStorage`에 둡니다. iOS로 가면 그대로 두기 어렵습니다 —
알림을 서비스 워커가 그려야 하는데, 워커에서 `localStorage`를 못 읽습니다. **IndexedDB
한 통으로 옮기고 `localStorage`는 옛 기록을 옮겨 담는 출발점으로만 남기는 것**이
맞습니다.

### 4. 시험 시간 재기 — 갈래가 넷입니다

| 갈래 | 등급 | 까닭 |
|---|---|---|
| 시간 셈 자체 | **A** | `Clock.java`는 안드로이드를 하나도 안 쓴다. `Date.now()`로 그대로 옮겨진다 |
| 화면 안 꺼지게 | **A/B** | Wake Lock — Safari 16.4+, 홈 화면 웹 앱은 **iOS 18.4**부터(그전엔 버그로 안 됐다) |
| 백그라운드에서 시간이 맞나 | **A** | 시작 시각을 저장하는 설계라 되돌아오면 저절로 맞는다 |
| **시간 다 됐을 때 알림** | **C / D** | 아래 |

앞의 셋이 A인 것은 설계 덕입니다. 남은 시간을 깎아 내려가는 대신 **시작 시각을
적어 두었기** 때문에, JS가 멈춰 있던 시간이 얼마든 돌아와서 빼기 한 번이면 맞습니다.
`Clock.java`의 `spent`/`left`/`face`/`record`는 안드로이드 클래스를 하나도 안 쓰므로
그대로 JS가 됩니다. 이미 `tests/test_twins.py`가 JS↔Java 중복을 감시하고 있으니
자리도 마련돼 있습니다.

**막히는 건 알림 하나입니다.** 안드로이드는 `setUsesChronometer`로 시스템이 카운트다운을
대신 그려 줘서, 앱이 잠들어 있어도 잠금 화면과 나우바에서 숫자가 흐릅니다.
iOS 웹에는 **예약 로컬 알림이 없습니다.** `Notification`은 지금 이 순간 띄우는 것이라
포그라운드에서만 쓸모가 있고, 백그라운드에서 정해진 시각에 뜨게 하려면 **그 시각에
누군가 푸시를 보내야 합니다.**

### 5. Web Push로 대신할 수 있나 — **C, 서버가 생긴다**

| | |
|---|---|
| Safari 탭 | **안 된다.** iOS의 Push API는 Safari 탭에 노출되지 않는다 |
| 홈 화면 웹 앱 | 된다 (iOS 16.4+) |
| 필요한 것 | Service Worker · Push API · VAPID 키 · **푸시를 예약해 보낼 서버** |
| 최소 | iOS 16.4. Declarative Web Push는 iOS 18.4+ |
| 권한·제스처 | **사용자 제스처 안에서** `Notification.requestPermission()` |
| 서버 | **필요하다** |
| GitHub Pages만으로 | **안 된다** |

되기는 됩니다. 타이머를 시작할 때 `시작시각 + 시험시간`에 푸시를 보내도록 예약해
두면, 그 시각에 알림이 뜹니다. Declarative Web Push(iOS 18.4+)를 쓰면 서비스 워커
없이도 알림이 그려지지만, **예약해 보낼 주체가 필요하다는 사실은 그대로입니다.**

그런데 이 하나 때문에 잃는 것이 큽니다.

- **서버가 생깁니다.** 지금 이 프로젝트는 서버가 없습니다. GitHub Pages 정적 파일과
  EBSi 링크가 전부입니다. 알림 하나를 위해 푸시 예약을 받아 둘 곳(Cloudflare Workers +
  Durable Object 알람 같은 것)이 필요해집니다.
- **구독 endpoint를 어딘가에 적어야 합니다.** "계정도 서버도 없으므로 이 기기 밖에는
  아무것도 없습니다"라는 README의 문장이 더 이상 참이 아니게 됩니다.
- 카운트다운은 못 그립니다. iOS 알림에는 흐르는 시계가 없어서, **끝났다는 한 번의
  알림**으로 바뀝니다.

**대안: 서버를 안 두는 길.** 앱이 앞에 떠 있는 동안에는 알림도 진동도 필요 없습니다 —
화면의 칩이 이미 흐르고 있습니다. 뒤로 갔다가 돌아오면 시간은 정확히 맞습니다.
잃는 건 **딴 앱을 보고 있는 동안 끝났다고 알려 주는 것** 하나뿐입니다. 그 하나를
위해 서버를 세울지는 값을 재 볼 만한 문제이고, 저라면 처음 판에는 안 세웁니다.

참고로 **진동은 어차피 안 됩니다** — `navigator.vibrate`는 iOS Safari에 없습니다.
`buzz()`는 옮길 자리가 없습니다(**D**).

### 6. 다른 앱 위에 띄우기 (FloatService) — **D**

| | |
|---|---|
| Safari 탭 · 홈 화면 웹 앱 | **둘 다 안 된다** |

웹에는 다른 앱 위에 그릴 방법이 없습니다. `TYPE_APPLICATION_OVERLAY`에 대응하는
것이 없고, `FLAG_NOT_TOUCHABLE`로 터치를 통과시키는 것은 더더욱 없습니다. 창 셋을
따로 놓고 각각 깃발을 다는 구조(`FloatService` 2,005줄)는 통째로 옮길 데가 없습니다.

**iPad는 반쯤 비슷한 것이 있습니다.** Split View·Slide Over·Stage Manager로 웹 앱을
다른 앱 옆에 둘 수 있습니다. 다만 이건 **사용자가 OS에서 하는 일**이지 우리가
부르는 API가 아니고, 나란히 놓는 것이지 위에 겹치는 게 아니며, 투명도도 터치 통과도
없습니다. 아이폰에는 그것마저 없습니다.

### 7. PiP로 우회할 수 있나 — **D**

Document Picture-in-Picture API는 Chrome 130·Edge 130에 있고 Firefox 151에 예정돼
있습니다. **Safari에는 없고 예정도 없습니다.**

영상 PiP는 iOS에 있으므로, canvas를 `captureStream()`으로 영상으로 만들어 PiP에
띄우는 술수를 떠올릴 수 있습니다. **권하지 않습니다.** PiP 창은 영상 표면이라
터치가 안 통합니다 — 쪽을 넘기지도, 확대하지도, 스크롤하지도 못합니다. 문제지를
띄워 두는 요점은 **보면서 조작하는 것**인데 그게 빠지면 남는 게 없습니다.

### 8. PickerView / Catalog — **A** (사실은 없어집니다)

`PickerView`(436줄)와 `Catalog`(298줄)가 있는 까닭은 **띄운 창 안에서 WebView 없이
과목을 고르게 하려면 자료를 자바가 따로 읽어야 했기** 때문입니다. 웹에는 자료가
이미 JS 안에 있고 화면은 이미 DOM입니다. 띄운 창이 없어지면 이 둘의 존재 이유도
함께 없어집니다. 옮길 것이 없는 게 아니라 **옮길 필요가 없습니다.**

### 9. 홈 화면 위젯 여섯 — **D** (하나만 **C**)

| | |
|---|---|
| Safari 탭 · 홈 화면 웹 앱 | **둘 다 안 된다** |

웹 앱은 iOS 위젯도, 제어 센터 컨트롤도, App Intents도 만들 수 없습니다. 아이콘
길게 눌러 나오는 바로가기도 없습니다. 이건 iOS 26에서도 그대로입니다 — 26이 바꾼
것은 **설치 문턱**(이제 어떤 사이트든 홈 화면에 넣으면 웹 앱으로 열립니다)이지
위젯이 아닙니다.

대신 있는 것은 **배지 하나**입니다.

| | |
|---|---|
| 필요한 것 | `navigator.setAppBadge()` |
| 최소 | iOS 16.4 |
| 권한 | **알림 권한이 있어야 배지가 보인다** |
| 어디 | **홈 화면 웹 앱 전용.** Safari 탭·WKWebView에는 노출 안 됨 |

아이콘 위의 숫자 하나입니다. D-day나 안 푼 개수 하나는 담을 수 있습니다. 달력·이번
주·잔디밭·최근 푼 것·다음에 풀 것은 **담을 데가 없습니다.**

게다가 배지도 **우리 코드가 돌 때만** 바뀝니다. 앱이 닫혀 있는 동안 D-day를 하루씩
줄이려면 다시 푸시가 필요하고, 푸시에는 다시 서버가 필요합니다. 백그라운드 동기화
(Background Sync·Periodic Background Sync)는 iOS에 없습니다.

### 10. 백업 — 내보내기·가져오기는 **A**, 자동은 **D**

| | 등급 | 어떻게 |
|---|---|---|
| 내보내기 | **A** | `navigator.share({files})` (iOS 15+) 또는 `<a download>` |
| 가져오기 | **A** | `<input type="file">` — 파일 앱이 열리고 iCloud Drive도 그 안에 있다 |
| **자동 백업** | **D** | 아래 |

자동 백업이 안드로이드에서 되는 까닭은 SAF에서 **자리를 한 번 고르면 그 권한이
남아**(`takePersistableUriPermission`) 그 뒤로는 같은 파일에 말없이 덮어쓸 수 있기
때문입니다. iOS 웹에는 이에 대응하는 것이 **아무것도 없습니다.** `showSaveFilePicker`를
비롯한 File System Access의 선택기들은 macOS·iPadOS·iOS 어느 Safari에도 없습니다.
WebKit이 구현한 것은 **OPFS**(우리 앱 안의 사설 저장소)뿐이라, 사용자가 볼 수 있는
파일에는 손이 닿지 않습니다.

**대신할 수 있는 것은 반자동입니다.** 지금도 `offerBackup()`이 표시가 20개를 넘으면
백업을 권합니다. iOS에서는 그것이 유일한 길이 됩니다 — 때가 되면 재촉하고, 사용자가
한 번 눌러 공유 시트로 내보냅니다. 자동이 아니라 **잊지 않게 해 주는 것**입니다(**C**).

### 11. 파일 앱 · iCloud Drive와의 연동 범위

| 하고 싶은 것 | 되나 |
|---|---|
| 파일 앱에서 백업 파일 고르기 | **된다** — `<input type="file">` |
| 파일 앱/iCloud Drive로 내보내기 | **된다** — 공유 시트가 그 자리를 다 준다 |
| 폴더째 고르기 | **안 된다** — `webkitdirectory`는 iOS Safari에 없다 |
| 같은 파일에 말없이 덮어쓰기 | **안 된다** |
| **받아둔 문제지가 파일 앱에 보이게** | **안 된다** — `UIFileSharingEnabled`는 네이티브 전용 |

마지막 줄이 실질적인 손해입니다. 안드로이드에서는 받아둔 PDF가 진짜 파일이라 다른
뷰어로도 열리고 파일 앱에서 보입니다. iOS 웹에서는 Cache Storage 안에 있으므로
**우리 화면 밖에서는 존재하지 않습니다.** 밖으로 내보내려면 그때마다 공유 시트를
거쳐야 합니다.

### 12. localStorage + SharedPreferences 이중 저장 — 웹에서는 **하나로 줄어듭니다**

지금 두 벌인 까닭은 위젯과 알림을 **WebView 없이 자바가** 그려야 하기 때문입니다.
`setSolved`가 페이지의 기록을 `SharedPreferences`로 옮겨 적고, `Solved.java`가 그걸
읽어 위젯을 그립니다.

iOS 웹에는 그 두 번째 독자가 없습니다 — 위젯이 없으니까요. **그러므로 이중 구조는
그냥 사라집니다.** 다만 통은 바꿔야 합니다.

```
현재:  page → localStorage
              ↘ NATIVE.setSolved → SharedPreferences → 위젯·자동 백업

iOS:   page ⇄ IndexedDB ⇄ Service Worker (알림을 그릴 때)
```

`localStorage`가 아니라 **IndexedDB**여야 하는 이유는 하나뿐입니다 — 서비스 워커가
읽어야 하고, 워커에는 `localStorage`가 없습니다. 푸시 알림을 안 쓰기로 하면
`localStorage` 그대로도 돌아갑니다.

### 13. PDF 공유 · 다른 앱으로 열기 — **A / B**

| | |
|---|---|
| 필요한 것 | `navigator.share({files:[File]})` |
| 최소 | iOS 15 |
| 권한·제스처 | **사용자 제스처 안에서 불러야 한다** |
| 서버 | 필요 없음 |

공유는 **A**입니다. 페이지가 이미 이 길을 갖고 있습니다 — 앱에서는 `NATIVE.shareFile`,
웹에서는 Web Share, 안 되면 다운로드로 떨어집니다. CORS가 열려 있으니 PDF를 `Blob`으로
받아 `File`로 싸서 넘기는 것까지 그대로 됩니다.

"다른 앱으로 열기"는 **B**입니다. 안드로이드는 `FileProvider` + `ACTION_VIEW`로 특정
앱을 겨냥할 수 있지만, iOS에는 그런 게 없고 **공유 시트가 유일한 길**입니다. 한 단계
더 거칩니다.

### 14. App Links에 대응하는 것 — **D**

| | |
|---|---|
| Safari 탭 · 홈 화면 웹 앱 | **둘 다 안 된다** |

`https://mangom72.github.io/Direct-mogo/…` 링크를 눌렀을 때 설치된 웹 앱이 받는 길은
없습니다. Universal Links(`apple-app-site-association`)는 **네이티브 앱의 App ID를
요구**하므로 웹 앱만으로는 성립하지 않습니다. `docs/assetlinks.json`에 대응하는 iOS
파일을 놓아도 받을 앱이 없으면 아무 일도 안 일어납니다.

**그리고 이것보다 더 아픈 게 하나 있습니다.** 홈 화면 웹 앱은 Safari와 **저장소를
따로 씁니다.** 같은 주소인데도 아이콘으로 연 것과 Safari로 연 것의 `localStorage`·
IndexedDB가 서로 남남입니다. 그래서 사용자가 어느 날 Safari에서 사이트를 열면
**푼 기록이 하나도 없는 화면**을 보게 됩니다. 안드로이드에는 이런 함정이 없습니다 —
앱과 브라우저가 같은 페이지를 봐도 앱은 `savedSolved()`로 제 사본을 갖고 있습니다.

iOS로 간다면 이 갈라짐을 **화면에 대놓고 알려 주고**, 백업 내보내기를 지금보다 훨씬
세게 권해야 합니다. 이건 기능이 아니라 사고를 막는 문제입니다.

### 15. PWA standalone · 서비스 워커 · 오프라인 실행 — **A**

이미 됩니다. `manifest.webmanifest`에 `display: standalone`이 있고 `sw.js`가 셸을
통째로 담아 둡니다. **iOS 26부터는 홈 화면에 추가한 사이트가 기본으로 웹 앱으로
열립니다** — 설치 요건이 아예 없어졌습니다.

손볼 것 하나: iOS에는 `beforeinstallprompt`가 없으므로 **"공유 → 홈 화면에 추가"를
손으로 안내해야** 합니다. 지금 안드로이드 브라우저에 띄우는 앱 권유 막대의 iOS판이
필요하고, 위의 저장소 갈라짐 때문에 그 막대는 권유가 아니라 거의 필수 안내입니다.

### 16. 앱 자체 업데이트 — **A, 그리고 코드가 없어집니다**

`Updater.java` 257줄, `REQUEST_INSTALL_PACKAGES` 권한, sha256 대조, 서명 확인,
`app/latest.json` 명세 — 이 전부가 **스토어를 안 거치기 때문에** 있는 것입니다.

웹에는 이미 있습니다. `sw.js`의 `check()`가 `index.html`을 조건부로 받아 달라졌으면
캐시를 갈아끼우고 페이지에 알립니다. **그게 곧 업데이트입니다.** iOS로 가면 이
기능은 옮기는 게 아니라 **사라집니다.**

### 그대로 옮길 수 있는 것

조회 · 내 과목 · 푼 회차 표시 · 진도 · 달력 · 다크 모드 · 주소 공유 · D-day ·

자체 업데이트(이미 서비스 워커가 함).

**앱이 하는 일의 대부분입니다.** 페이지가 이미 하고 있거나, `Clock.java`처럼
안드로이드를 안 쓰는 순수 계산이거나, 웹 표준이 그대로 대응합니다.

### 방식만 바꾸면 유지되는 것

| 기능 | 바뀌는 것 |
|---|---|
| PDF 뷰어 | `PdfRenderer` → pdf.js. 제스처·스크롤바 새로 씀. **타일 렌더링 필수** |
| 저장 위치 | 앱 폴더의 진짜 파일 → Cache Storage. 밖에서는 안 보임 |
| 기록 저장 | `localStorage` + `SharedPreferences` → **IndexedDB 한 통** |
| 자동 백업 | 저절로 덮어쓰기 → **때맞춰 재촉하고 한 번 누르기** |
| 위젯 여섯 | → **배지 숫자 하나** (D-day 정도) |
| 다른 앱으로 열기 | 특정 앱 겨냥 → 공유 시트 |
| 타이머 종료 알림 | 로컬 알림 → **Web Push (서버가 생긴다)** |

마지막 줄만 성격이 다릅니다. 나머지는 코드를 바꾸는 일이지만, 이것은 **프로젝트의
전제를 바꾸는 일**입니다 — 서버 없음·계정 없음이라는 성질을 알림 하나와 맞바꿉니다.

### iOS 네이티브 앱 없이는 안 되는 것

1. **다른 앱 위에 문제지 띄우기** — 투명도·터치 통과·창 셋 전부
2. **홈 화면 위젯 여섯** — 웹 앱에 위젯·컨트롤·App Intents가 없음
3. **알림의 흐르는 카운트다운** — iOS 알림에 시계가 없음
4. **자동 백업** — 지속되는 쓰기 권한이 없음
5. **받아둔 문제지가 파일 앱에 보이는 것**
6. **App Links** — Universal Links는 네이티브 App ID를 요구
7. **진동**

일곱 중 1·2가 값의 대부분입니다. **띄운 창과 위젯을 포기할 수 있으면 iOS 웹으로
갈 만하고, 그 둘이 요점이면 갈 수 없습니다.**

```js
…
if(NATIVE && NATIVE.pickAutoBackup){ /* 자동 백업 단추를 그린다 */ }
```

`index.html` 안에 `NATIVE && NATIVE.무엇` 꼴의 확인이 마흔 군데 가까이 흩어져
있습니다. 이 한 줄은 **두 가지를 뒤섞고 있습니다.**

- "안드로이드 앱인가"
- "자동 백업을 할 수 있는가"

지금은 둘이 같은 말이라 문제가 안 됩니다. iOS가 들어오면 갈라집니다 — iOS 웹 앱은
알림은 되고 자동 백업은 안 되고 위젯도 안 됩니다. 갈래가 셋이 아니라 **능력의
격자**가 됩니다.

### 제안하는 모양

창구(메서드)가 아니라 **능력**으로 가릅니다.

```js
const CAP = pickBackend();      // android | ios | web

if(CAP.can("autoBackup")) drawAutoBackupButton();
CAP.openPaper(url, name, {grade, sub, key});
```

`pickBackend()`가 하는 일은 셋입니다.

1. **어느 뒤판인지 고른다** — `GijulNative`가 있으면 안드로이드, 없으면 웹.
2. **능력표를 채운다** — 안드로이드는 창구가 실제로 있는지 하나씩 물어서, 웹은
   `"share" in navigator` 같은 기능 검출로.
3. **이름을 맞춘다** — 호출부는 한 가지 이름만 안다.

### 이 모양이 지금 당장 갚는 값

iOS를 안 하더라도 이득이 둘 있습니다.

**하나, 인자 수 갈래가 호출부에서 사라집니다.** 지금 이렇게 돼 있습니다.

```js
if(NATIVE.openPaperAt && key) NATIVE.openPaperAt(a.href, a.dataset.nm, sel.grade, sel.sub, key);
else if(NATIVE.openPaperIn)   NATIVE.openPaperIn(a.href, a.dataset.nm, sel.grade, sel.sub);
else                          NATIVE.openPaper(a.href, a.dataset.nm);
```

옛 앱을 위한 갈래인데, 이게 호출부에 드러나 있습니다. 창구를 하나 더 낼 때마다
이 사다리가 한 칸씩 깁니다. 어댑터가 삼키면 호출부는 한 줄이 되고, 사다리는 어댑터
안 한 곳에만 있습니다. **`docs/split.md`에 적어 둔 '규칙 1'을 지키기가 훨씬 쉬워집니다.**

**둘, 웹 갈래가 눈에 보입니다.** 지금 웹 대체 구현(Web Share 폴백, 낱개 다운로드)은
`NATIVE`가 거짓일 때의 `else` 가지로 흩어져 있어, 무엇이 웹에서 어떻게 도는지 읽어
내려면 마흔 군데를 따라가야 합니다. 어댑터가 있으면 웹 뒤판 한 곳에 모입니다.

### 하지 말아야 할 것

- **어댑터를 두껍게 만들지 않습니다.** 하는 일은 이름 맞추기와 능력 답하기까지입니다.
  "백업할 때가 됐는가" 같은 판단은 페이지에 남깁니다. 뒤판마다 정책이 갈리기 시작하면
  같은 버그를 두 번 고치게 됩니다.
- **`GijulNative`의 창구 이름은 그대로 둡니다.** 그건 이미 나간 앱과의 약속이고,
  어댑터는 그 위에 덮는 것이지 바꾸는 것이 아닙니다.
- **`Clock` 같은 순수 계산은 어댑터에 넣지 않습니다.** 그건 능력이 아니라 규칙이라
  양쪽이 같아야 합니다. 오히려 **웹을 정본으로 삼고 자바가 그것을 베끼는 방향**이
  맞고, `tests/test_twins.py`가 이미 그 어긋남을 잡고 있습니다.

### 순서

1. **어댑터를 먼저 넣습니다** (iOS와 무관하게). 능력표 + 안드로이드 뒤판 + 웹 뒤판.
   `tests/`가 지금 지키는 것이 그대로 지켜지는지만 보면 됩니다.
2. **pdf.js 뷰어를 웹 뒤판에 붙입니다.** 여기서 웹이 앱과 가장 크게 벌어지고,
   CORS가 열려 있는 덕에 가능한 일입니다. **이게 되면 나머지는 대부분 따라옵니다.**
3. **홈 화면 안내와 저장소 갈라짐 경고**를 넣습니다. 기능이 아니라 사고 방지입니다.
4. 알림은 **맨 나중에**, 그때 서버를 세울지 결정합니다. 안 세워도 나머지는 다 돕니다.
